# Style guide

How code in this repository is written. [AGENTS.md](../AGENTS.md) holds the binding architecture, security and privacy rules; this guide adds the conventions that make the code read the same everywhere. Rules marked **(checked)** are enforced by CI.

## General

- Code, identifiers, comments, commit messages and documentation are in English. A domain term without a good English equivalent keeps an English identifier and names the original once in a comment (for example Lab Rules / _Laborordnung_).
- The repository contains only implemented features. Prototypes live on branches, plans and progress notes in issues or pull requests — not in `docs/` or `src/`.
- Comments explain _why_ (an invariant, a security reason, a non-obvious constraint), not _what_ the next line does.
- Commit messages: imperative or descriptive subject line about the user-visible effect, blank line, a short body. One logical change per commit.

## Go

### Layout

- One package per business feature under `backend/internal/<feature>/`, with `service.go` (constructor and public API), one file per sub-topic (`jobs.go`, `runs.go`) and `db/` for sqlc. Files above ~1200 lines (after formatting) are split by sub-topic.
- `internal/httpapi` is the only HTTP adapter: one file per feature, each handler parses the request, calls exactly one service method and maps the result. `server.go` holds only the `Server` struct and its wiring.
- `internal/platform/*` holds shared plumbing (config, database, errors, logging, rate limiting, telemetry). Feature code does not grow private copies of platform helpers.
- Domain packages do not import `internal/openapi`. The permission registry in `internal/authorization` is the single, documented exception.

### Formatting **(checked)**

- `gofmt`; lines target 120 columns (`golines -m 120`), hard limit 160 (`lll`). Long SQL and message literals may exceed it.
- Struct literals with more than three fields and calls with long argument lists put one field or argument per line.
- One blank line between top-level declarations.

### Errors

- Client-visible errors are `*apperror.Error` built with `apperror.New(http.Status…, "snake_case_code", "Sentence.")`. Status codes are always `http.Status…` constants, never numeric literals.
- Throttling uses `apperror.RateLimited(code, message, retryAfter)` with the window of the limiter that fired; the HTTP layer turns it into `Retry-After`.
- Internal errors wrap with context: `fmt.Errorf("load spool %s: %w", id, err)`. Go error strings start lowercase and have no trailing punctuation.
- Never put request data, SQL text or secrets into `Message`, `Details` or logs. The HTTP layer logs SQLSTATE and constraint names only.
- Compare errors with `errors.Is`/`errors.As`, never `==`.

### Transactions and persistence

- All SQL lives in `db/queries.sql` and is generated by sqlc. No inline SQL in Go.
- A service method that mutates opens the transaction, takes the locks in the documented order (Account before credentials, people before accounts), writes the audit event in the same transaction and commits.
- Deferred rollback has one form: `defer func() { _ = tx.Rollback(ctx) }()`.
- Slow work (Argon2, external calls, file I/O) happens before the transaction opens or after it commits; re-validate under the lock that nothing changed.

### Types and names

- Enumerated domain values are typed: `type RunOutcome string` with a `const` block. Raw string literals for states are confined to the persistence mapping.
- Constructors take every dependency explicitly; no variadic optional dependencies.
- Size, time and count limits are named constants defined once, in the package that enforces them, and exported when the HTTP layer needs the same value.
- Package names are lower case without underscores and name the feature (`opendays`, `machinelogbook`). A local daemon and the Core module that manages it share a stem: the singular is the daemon (`printerconnector`, `streaminggateway`), the plural is Core's registry of them (`printerconnectors`, `streaminggateways`). Every package has a `// Package …` comment saying which side it is.

### HTTP

- Which operations need a staff session, which take a raw binary body, and which may be revalidated are derived from `api/openapi.yaml` (`security`, `requestBody`) via `internal/httpapi/route_policy.go`. Do not add path-prefix checks for these rules.
- Per-operation body limits live in `requestBodyLimits`, keyed by `routeKey(method, pathTemplate)`.
- Every API response is `Cache-Control: no-store` unless the route is listed as revalidated or the handler sets its own policy for public, content-addressed data.

### Tests

- Every authorization-sensitive behaviour has a positive and a negative test. Repository and API behaviour is tested against real PostgreSQL in `backend/tests/integration`.
- Test files and test names describe the behaviour under test (`pin_throttle_test.go`, `TestPINThrottleBacksOffAndForgetsQuietSources`), not the occasion that produced them.
- Tests assert invariants, not counts of things that legitimately grow (number of operations, number of routes).

### Linting **(checked)**

`golangci-lint run` with `backend/.golangci.yml`: the standard set plus `bodyclose`, `errorlint`, `gosec`, `lll`, `misspell`, `nilerr`, `unconvert`, `usestdlibvars`. A `//nolint:<linter> // <reason>` is allowed only on a single line with a concrete reason.

## SQL and migrations

- One goose migration per schema change, always with a working `Down`; `DO` blocks are wrapped in `-- +goose StatementBegin/End`. Applied migrations are never edited.
- sqlc query names are `VerbObject[ByKey]` (`GetAccountForAuthentication`). Queries that lock (`FOR UPDATE`) say so in the name or a comment.
- Identifiers are UUIDv7 generated in Go; timestamps are `timestamptz` in UTC.

## OpenAPI

- `api/openapi.yaml` is the HTTP contract. Generated Go and TypeScript are regenerated in the same change and never edited by hand.
- `operationId`s are stable lower camel case; responses use the shared error envelope; every expected success and error response is modelled.
- Passwords and tokens are `writeOnly`; examples never contain real credentials or personal data.
- PATCH bodies keep the difference between an omitted field and an explicit `null`.
- An operation's `security` entry is authoritative: an operation without `sessionCookie` is reachable without a staff session.

## TypeScript and React

### Formatting **(checked)**

- Prettier (`frontend/.prettierrc.json`: 120 columns, single quotes, trailing commas); `pnpm format` rewrites, CI runs `pnpm format:check`. Generated client code is excluded.

### Structure

- `src/features/<feature>/` with `XPage.tsx` for routes, `queries.ts` for query keys and options, `components/` and `dialogs/`. Components stay below ~600 formatted lines; larger pages are split into sections, dialogs and hooks.
- Shared building blocks live in `src/app/`. The generated client in `src/api/generated/` is the only way to call the API; `apiFetch` directly is reserved for binary downloads and is commented where used.

### State

- Server state: TanStack Query. Forms with more than two fields: React Hook Form. Local UI state: `useState`.
- Secrets (passwords, PINs, tokens, SMTP credentials) only go through `useSecretMutation`; never into URLs, query keys, mutation variables or browser storage.
- Derive values during render instead of synchronising them with `useEffect`. `react-hooks/exhaustive-deps` is never suppressed; use `useLatestCallback` for callbacks that must not retrigger effects.
- `useMemo`/`useCallback` only where identity matters (effect dependencies, query keys, object URLs that must be revoked) or where a measurement shows a cost; say which in a short comment.

### Styling

- IBM Carbon components, icons and pictograms first. Handwritten controls only where Carbon has no equivalent, with a comment saying so.
- Colours, spacing and type come from Carbon's Sass tokens (`@use '@carbon/styles/scss/theme' as theme;` → `theme.$text-secondary`, `spacing.$spacing-05`, type mixins). Never write a bare `var(--cds-…)`: the default theme does not define those custom properties, and only the Sass tokens carry the fallback value. Fixed pixel values are for application-specific rendering only (signage scenes at display resolution, hairlines, print layouts).
- Each Carbon component adds only its own `@carbon/styles` module; never the full `@carbon/react` stylesheet. Chart code and chart CSS stay behind the asynchronous charting boundary.

### Dependencies **(checked)**

- Versions are pinned exactly (no `^` or `~`). A new runtime dependency needs a bundle measurement in its pull request.
- The production build enforces the bundle budget: initial JavaScript ≤ 225 kB gzip, entry CSS ≤ 80 kB gzip.

### Verifying UI changes

- A UI change is not done because it compiles and the tests pass. Open the affected page in a real browser, check layout, spacing, overflow, focus and the loading, empty, error, disabled and destructive-confirmation states, and look for console errors.
- Check desktop and a narrow viewport (320–414 px) when layout or loading behaviour changes.
- Prefer Playwright with axe checks for flows; avoid pixel-perfect snapshot tests.

## Delivery and operations

- Production images are built from pinned base images. GitHub Actions are pinned to commit SHAs with the version in a comment.
- nginx serves HTML with the security headers in `frontend/nginx/` (CSP with `frame-ancestors 'none'` and no inline scripts, HSTS, `nosniff`, Referrer-Policy, Permissions-Policy). A new external origin the browser must reach is added to the matching CSP snippet in the same change.
- Secrets come from the environment; examples in `*.env.example` are empty or obviously fake.

## Settings screens

Settings screens are registered in `frontend/src/features/settings/settingsCatalog.ts` (group, title, description, path, icon, permissions). The overview, the route guard permissions and each screen's breadcrumb (`Settings / Group / Page`) derive from it, so a new settings screen is added there and rendered inside `SettingsPageLayout`. Screens that belong together are one page with `SettingsTabs` (selection in `?tab=`); each tab appears only for people holding its permission, and old per-tab routes redirect to the tab. Use `SettingsSection` for titled blocks, `SettingsLoading` for loading placeholders, `EmptyState` for empty lists and inline notifications for save results; put the primary Save action last in a form's action row, after Cancel or Reset.
