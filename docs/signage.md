# Digital signage

Centrally managed information and advertising screens for one makerspace. Displays run a small, separate player web app in a Chromium kiosk. Content, rules and devices are managed in Core; printer camera video stays inside the makerspace LAN and flows through a local streaming gateway.

This document is the implementation contract for digital signage.

## Concepts

| Concept               | Meaning                                                                                                                                                       |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Display               | One physical screen. Bound 1:1 to a managed device whose only application mode is `signage_player`.                                                           |
| Scene                 | One screen composition: a zone **layout template** (fixed set, defined in code) plus one widget per zone, background colour/image, text theme.                |
| Playlist              | Ordered scenes with seconds per item and a transition (`cut`, `fade`).                                                                                        |
| Rule                  | Per display, ordered. "When _condition_ show _scene or playlist_". First enabled match wins; the display's default playlist is the fallback.                  |
| Publication           | Immutable manifest per display: rules, default playlist and every scene, playlist and asset they reach, at publish time. Players only ever play publications. |
| Asset                 | An uploaded image or video (metadata here, bytes in the existing files/storage module).                                                                       |
| Announcement template | Fields (typed inputs) + title/body with `{placeholders}` + tone.                                                                                              |
| Announcement          | A started instance of a template: values, target displays (all or selected), start, optional end. Live data, never published.                                 |
| Streaming gateway     | Headless local service (Go) that registers with Core, controls a bundled go2rtc, and serves camera streams to players on the LAN with ticket checks.          |

## Permissions (registered; never role names)

| Permission               | Allows                                                                                |
| ------------------------ | ------------------------------------------------------------------------------------- |
| `signage.read`           | Read displays, health, content, media, rules, announcements                           |
| `signage.manage`         | Pair, rename, revoke, delete displays; edit rules, default playlist, display settings |
| `signage.content.manage` | Create/edit/delete scenes, playlists, assets, announcement templates                  |
| `signage.publish`        | Publish a display                                                                     |
| `signage.override`       | Start, edit, stop announcements                                                       |
| `local_services.manage`  | Manage streaming gateways and camera assignments; issue enrollment secrets            |

Every write permission implies nothing else; services check exactly what they need and the frontend hides controls accordingly (UX only).

## Data model (migrations `00051_signage.sql`, `00052_signage_player_mode.sql`, `00053_streaming_gateways.sql`)

UUIDv7 ids generated in Go, `timestamptz` UTC, `version int` for optimistic concurrency on editable rows (`expectedVersion` on writes, 409 `stale_write`). JSONB only for the scene zone tree and publication manifests.

- `signage_displays`: id, managed_device_id (unique, FK managed_devices ON DELETE RESTRICT), name, location, orientation (`portrait`|`landscape`), resolution_width/height, visible_from_outside bool, default_playlist_id (FK, RESTRICT), revoked_at, created_at, updated_at, version.
- `signage_pairing_requests`: id, code_digest (unique among open requests), poll_secret_digest, created_at, expires_at (15 min), claimed_display_id (nullable FK), claimed_at, delivered_at. Rows are deleted after delivery or expiry (cleanup on access + periodic sweep is not needed; delete expired rows opportunistically in the same statements).
- `signage_assets`: id, file_id (FK files, RESTRICT), kind (`image`|`video`), name, width, height, duration_ms (nullable), created_by_account_id, created_at.
- `signage_scenes`: id, name, orientation, layout_id (text, validated against the code-defined layouts), background_color (`#rrggbb`), background_asset_id (nullable FK RESTRICT), background_fit (`cover`|`contain`), background_dim (0–80), theme (`dark`|`light`), zones jsonb, created_at, updated_at, version.
- `signage_playlists`: id, name, created_at, updated_at, version. `signage_playlist_items`: playlist_id, position, scene_id (FK RESTRICT), seconds (3–3600), transition. PK (playlist_id, position).
- `signage_rules`: id, display_id (FK CASCADE), position, enabled, condition_kind (`time_window`|`machine_printing`|`announcement_active`|`live_data_unavailable`), weekdays smallint[] (ISO 1–7), time_from/time_to (time, may wrap midnight), machine_ids uuid[], machine_match (`any`|`all`), announcement_template_ids uuid[] (empty = any), target_kind (`scene`|`playlist`), target_scene_id / target_playlist_id (exactly one, FK RESTRICT), min_seconds (0–600, default 20), multi_mode (`split`|`alternate`), alternate_seconds. CHECK constraints per kind. Unique (display_id, position) DEFERRABLE.
- `signage_publications`: id, display_id (FK CASCADE), revision (per display, starting 1), manifest jsonb, manifest_sha256, published_by_account_id, published_at. Unique (display_id, revision). Keep the latest 5 per display.
- `signage_display_states` (ephemeral, not audited): display_id PK, last_heartbeat_at, publication_revision, current_rule (text: rule id, `default`), current_scene_id, player_version, cache_used_bytes, cache_quota_bytes, errors jsonb (max 20 short entries, no PII).
- `signage_announcement_templates`: id, name, tone (`info`|`warning`|`critical`|`neutral`), title, body, created_at, updated_at, version. `signage_announcement_template_fields`: template_id, position, key (`^[a-z][a-z0-9_]{0,39}$`, not a built-in), label, type (`text`|`longtext`|`time`|`date`|`datetime`|`number`|`choice`|`machine`), required, default_value, helper_text, options text[] (choice only).
- `signage_announcements`: id, template_id (FK RESTRICT), all_displays bool, starts_at, ends_at (nullable), created_by_account_id, created_at, updated_at, version. `signage_announcement_values`: announcement_id, key, value (text ≤ 2000). `signage_announcement_displays`: announcement_id, display_id. Ended announcements are hard-deleted after 30 days (on access) — no indefinite retention of message content.
- Gateway phase (`00053_streaming_gateways.sql`): `streaming_gateways` (id, name, public_host, lifecycle `pending|active|disabled|revoked`, configuration revision, heartbeat fields, version), `streaming_gateway_enrollments` and `streaming_gateway_credentials` (mirroring the printer connector tables: digests only), `streaming_cameras` (id, gateway_id CASCADE, machine_id UNIQUE → `machines` CASCADE, enabled, version), `streaming_camera_states` (ephemeral heartbeat health) and `signage_ticket_keys` (Ed25519 key pairs, private key encrypted with the application keyring, exactly one active row). Camera RTSPS host/access code are **not** duplicated: they come from the machine's active Bambu printer-connector assignment settings and encrypted secrets (`ipAddress`, `lanAccessCode`) at configuration time.

Every mutation writes its audit event in the same transaction (`audit.Write`, changed field names only; never announcement values or token material). Pairing, heartbeats and live reads are not audited, except pairing claim and device revoke.

## Scene zones (JSONB, validated in Go)

`zones` is an object `{ "<zoneId>": Widget }`; zone ids must belong to the layout. Unknown keys are rejected (strict decoding), text lengths are capped, no HTML (plain text only, rendered as text nodes), URLs for QR codes must be `https://`. Widget types and fields are defined in `api/openapi.yaml` and `frontend/src/features/signage/` (`empty`, `image`, `video`, `slideshow`, `text`, `qr`, `clock`, `camera`, `status`, `open_days`, `events`, `announcement`). Layouts are a fixed, versioned list shared by backend validation (zone ids) and frontend rendering (grid CSS), defined once in `api/openapi.yaml` as an enum and in `frontend/src/features/signage/layouts.ts`.

## Publish and drafts

Scenes, playlists, rules, default playlist and display settings are drafts. `POST /signage/displays/{id}/publish` (signage.publish) builds the manifest from current drafts in one transaction, stores the publication and audits it. `GET /signage/displays/{id}` returns `publishedRevision`, `publishedAt` and `pendingChanges: [{kind, name, change}]`, computed by comparing the draft manifest with the latest publication (by entity id + version). Deleting a scene/playlist/asset referenced by drafts is a 409 listing references; anything only referenced by older publications may be deleted (players keep their cached copy until they get a new manifest).

## Player protocol

The player is unauthenticated until paired, then authenticates as its managed device (HttpOnly cookie, the existing managed-device cookie). A `signage_player` device may only call `/signage/player/*` (and the public pairing endpoints); it can never hold a staff session. All player responses are `Cache-Control: no-store` except content-addressed asset bytes.

1. **Pairing.** `POST /public/signage/pairing` → creates a request with a 6-character code from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (CSPRNG) and a 32-byte poll secret set as HttpOnly `SameSite=Strict` cookie; returns `{code, expiresAt}`. Rate-limited per client IP (e.g. 10/hour) and globally capped (e.g. 50 open requests). `GET /public/signage/pairing` (poll every 3 s, with that cookie) → `pending` | `expired` | `paired`. On the first `paired` poll the server creates the device token, sets the managed-device cookie, marks the request delivered and deletes it — the plaintext token never sits in the DB.
   Staff: `POST /signage/displays` `{code, name, location, orientation, resolution, visibleFromOutside, defaultPlaylistId}` (signage.manage) finds the open request by code digest, creates managed device (mode `signage_player`, no staff, no terminal), display and an empty first publication-ready state; unknown/expired code → 422 `pairing_code_invalid` (same message for both). Failed attempts are rate-limited per account.
2. **Manifest.** `GET /signage/player/manifest?known=<revision>` → 304-like `{unchanged: true}` or the full manifest `{revision, display: {orientation, resolution, visibleFromOutside}, rules, defaultPlaylistId, scenes, playlists, assets: [{id, kind, sha256, size, url}], layouts version}`. Assets: `GET /signage/player/assets/{assetId}/{sha256}` → bytes, `Cache-Control: private, max-age=31536000, immutable`, only if the asset is in the display's latest publication.
3. **Live.** `GET /signage/player/live` every ~10 s → `{serverTime, revision, machines: [{machineId, name, state, progressPercent, remainingMinutes, observedAt, stale}], announcements: [{id, templateId, tone, title, body, startsAt, endsAt}], openDays: [...next 5 public: startsAt, endsAt, status, competencies (public labels only)], events: [...next 5 public-safe: title, startsAt, location], streams: [{machineId, webrtcUrl, mseUrl, ticket, expiresAt}] }`. Machines are those referenced by the display's published rules/widgets; state comes from `printer_live_statuses`, stale when `received_at` is older than 3 minutes (state `unknown`). Announcements are rendered server-side (Go is authoritative; built-ins `{ends_at} {ends_on} {ends} {starts_at} {today} {display} {location}`; times in the makerspace time zone from config). No customer data, ever.
4. **Heartbeat.** `POST /signage/player/heartbeat` `{revision, currentRule, currentSceneId, playerVersion, cacheUsedBytes, cacheQuotaBytes, errors[]}` every 30 s → upserts `signage_display_states`. Display status: online if heartbeat < 90 s, otherwise offline.

The player evaluates rules locally (TypeScript engine shared with the admin preview: `frontend/src/features/signage/engine/`), so time windows keep working offline. `live_data_unavailable` matches when the last successful live poll is older than 60 s. Min display time is enforced by the player (a winning rule keeps the screen for at least `min_seconds` unless a higher-priority rule takes over). Announcement rendering also has a TypeScript copy for the admin live preview; both implementations run the same JSON test vectors (`api/testdata/signage-announcement-render.json`).

## Player app

Separate Vite entry `frontend/player.html` → `src/player/main.tsx`; no Carbon, no TanStack Query, no app shell; plain CSS. It must not import from `src/app` or Carbon packages (lint rule or test). Its own bundle budget: ≤ 90 kB gzip JS, ≤ 20 kB CSS; the service worker ≤ 4 kB gzip. Served by the same nginx at `/player/` with `Cache-Control: no-cache` for HTML.

- Screens: pairing code (big code, expiry countdown, regenerates on expiry), playing, fatal error.
- Offline (phase 4): a service worker (`src/player/sw.ts`, built to `/player/sw.js`, scope `/player/`, served `no-cache`) precaches the player shell (`/player/` plus the hashed JS/CSS of the player entry; the build fills the file list in from the Vite manifest) and answers `/api/v1/signage/player/assets/{id}/{sha256}` from Cache Storage (including byte ranges for videos). The runtime downloads every asset of a new manifest into the `signage-assets-v1` cache, keyed by sha256, and saves the manifest to `signage-state-v1`; only then does the revision activate. After activation, assets the active manifest does not reference are evicted. A cold start restores the persisted manifest (when all its assets are cached) and plays it without network; a network error never shows the pairing screen, only a 401/403 (or an unknown 404) does and then clears the cache. The player asks for persistent storage and reports `navigator.storage.estimate()` as `cacheUsedBytes`/`cacheQuotaBytes` in heartbeats; a revision whose missing assets exceed the free quota (or whose download hits `QuotaExceededError`) is refused, the old one keeps playing and the error is reported. Without Cache Storage (insecure origin) the player falls back to in-memory preloading. Only published content is stored: manifest, assets and the announcements/open days/events of the last live payload, never credentials or machine status.
- Live data lifetime: machine status shows "Status unknown" (and `live_data_unavailable` applies) after 60 s without a successful poll; machines are never restored from storage. Announcements are kept until their `endsAt`, open-ended ones until the next successful poll. Announcements, open days and events are persisted with a timestamp (rewritten when they change, otherwise every 5 minutes) and restored after a restart if younger than 24 h.
- Start order: the player asks for the manifest first. Live polling and heartbeats start only after that call was answered by the server with an authenticated response (or after a revision was restored from the cache), so an unpaired display makes no 401 requests besides the manifest call that sends it to pairing.
- Implemented in `frontend/src/player/`: `api.ts` (five-call fetch wrapper), `pairing.ts` (pairing loop), `runtime.ts` (revision activation after preload, live/heartbeat/manifest loops, backoff, revocation), `view.ts` (shared engine plus the `min_seconds` hold), `camera.ts` (`CameraSource` seam for phase 5: `hasStream` marks cameras without a stream unavailable, `view` supplies the picture through `RenderData.cameraView`). The import graph is enforced by an ESLint override and `src/player/imports.test.ts`; the budget (JS 90 kB, CSS 20 kB gzip) is checked per entry in `scripts/check-bundle-budget.mjs`. A 404 other than `signage_not_published` on a player endpoint is treated like a revoked credential.
- Kiosk: documented Chromium flags and a systemd unit example in `docs/signage-player.md` (autostart, watchdog restart, screen blanking off).

## Streaming gateway and cameras (phase 5)

Setup, ports, TLS and the hardware checklist are in [Streaming gateway](streaming-gateway.md). The contract in short:

- **Core side** (`backend/internal/streaminggateways`): gateway registry with lifecycle, one-time enrollment secret (15 min, digest stored), runtime credentials with rotation (90 days, 24 h handover) — the printer-connector pattern, separate tables. Gateway-authenticated endpoints under `/streaming-gateway/*` (`enroll`, `configuration`, `heartbeat`, `credential-rotation`) use their own bearer scheme and the connector rate limit (600 requests/minute per gateway). `local_services.manage` guards every administrative operation (OpenAPI tag "Local Services"): create/list/get/rename/disable/enable/revoke/delete gateways, issue enrollment secrets, assign/enable/disable/unassign cameras, `GET /local-services/cameras` (status of all cameras), `GET /local-services/camera-candidates` (machines with an active Bambu printer assignment and no camera yet: id, name, kind; the assign dialog uses it, so `machines.read` is not needed). Gateway responses carry `credentialExpiresAt` (expiry of the current credential, `null` while there is none), shown as "Credential expires" in the Local services list. Failed gateway authentications and enrollments (missing or unknown bearer token, wrong enrollment secret) are limited to 20 per client IP and 15 minutes; further requests from that address are answered 429 `rate_limited` until the window passes. The limiter is the shared in-memory `backend/internal/platform/ratelimit` (the pairing limits use it too); the printer connector endpoints are unchanged. Credentials and the camera source URL are never shown to administrators.
- **Configuration** (`GET /streaming-gateway/configuration`): `{revision, protocolVersion, publicHost, sessionEpoch, revokedDisplayIds, ticketPublicKeys: [{kid, publicKey, validUntil}], cameras: [{machineId, name, streamName, sourceUrl}]}`. `streamName` is `cam-` plus the machine id without dashes (stable). `sourceUrl` is built from the machine's active Bambu assignment: `rtspx://bblp:<lanAccessCode>@<ipAddress>:322/streaming/live/1` (`rtspx` is go2rtc's RTSPS without certificate verification, needed for the printers' self-signed certificates; **verify on hardware**). Cameras without an active H2D/X1C assignment are omitted. A disabled gateway receives no cameras. `revision` is bumped by every gateway, camera, key and session-epoch change; printer-assignment changes do not bump it, so the gateway compares the content of what it renders rather than the revision alone.
- **Camera assignment rules**: the machine must exist and have an active (not ended) `bambu_h2d` or `bambu_x1c` printer-connector assignment; each machine has at most one camera (409 `streaming_camera_exists`); revoked gateways accept no cameras.
- **Heartbeat** (every 30 s): software version, applied revision, `connected|degraded`, and per camera `live|idle|unavailable`, viewers, codec, width, height, fps. Stored ephemerally (`streaming_camera_states`, replaced per heartbeat, not audited). The status view treats reports older than 90 s as `unknown`.
- **Tickets**: Core signs `base64url(payload).base64url(signature)` with Ed25519 (`backend/internal/streamticket`, shared with the gateway). Payload `{v:1, displayId, machineId, streamName, exp, kid}`, valid 5 minutes; verifiers accept 30 s clock skew. Keys are created on first use. Rotation is staged (`POST /local-services/ticket-key/rotation`, `local_services.manage`, audited): the new key is `pending`, published to gateways at once and used for signing after at least 60 s (lazily with the first ticket after that, or immediately when rotation is requested again); the retired public key stays in gateway configurations for 10 minutes. A verifier rejects tickets that expire more than 5 minutes + 30 s ahead. Revoking a display stops new tickets; issued ones expire within 5 minutes, and running or unused sessions are cut through the gateway configuration (see below).
- **Player live data**: `streams` contains `{machineId, webrtcUrl, mseUrl, ticket, expiresAt}` for the cameras used by the display's **published** camera widgets (machine widgets; an `auto` widget makes every machine the publication watches through rules or status widgets a candidate), only while the camera is enabled and the gateway is `active`. URLs are `https://<publicHost>/api/webrtc?src=<streamName>` and `wss://<publicHost>/api/ws?src=<streamName>`; the player adds the ticket as `ticket` query parameter or `Authorization: Bearer`. The staff preview (`GET /signage/displays/{id}/preview`) never carries streams. Maximum 20 streams per response. **Displays visible from outside** (`visibleFromOutside`) get no streams unless the display setting `allowCameraOutside` (default off, audited as a changed field, only meaningful with `visibleFromOutside` but stored either way) is on. It takes effect immediately without a publication, because it only restricts live tickets; switching it off (or moving a display outside without it) bumps the session epoch. The display detail page warns ("Live cameras are not shown") while such a display's current publication contains a camera widget, because those widgets then only ever show their fallback.
- **Session epoch and revoked displays.** The gateway configuration carries `sessionEpoch` and `revokedDisplayIds` (displays revoked or deleted within 24 h, kept in `signage_revoked_displays`). The epoch (table `streaming_session_epoch`) and every gateway's configuration revision are bumped in the same transaction as the triggering change: revoking or deleting a display, publishing a display without a camera its previous publication used, and switching camera access outside off. The gateway restarts go2rtc when the epoch changes, which ends all running sessions (players reconnect with fresh tickets) and refuses tickets of listed displays. Guarantee and limits: [Streaming gateway](streaming-gateway.md#security-model).
- **Gateway binary** (`backend/cmd/streaming-gateway`, `backend/internal/streaminggateway`): enrolls with the one-time `STREAM_ENROLLMENT_SECRET` (legacy: `STREAM_ENROLLMENT_SECRET_FILE`), keeps identity and last configuration encrypted in its data directory, polls every 30 s (keeps serving the last configuration while Core is unreachable; three consecutive 401 answers switch streaming off), renders go2rtc's YAML (streams only; API on the internal network with generated credentials and a four-path allow list, exec/echo sources disabled, log level `error`, no RTSP/SRTP server, no UI/static directory, WebRTC candidates from the host LAN address), restarts go2rtc through `POST /api/restart` when the rendered file or the session epoch changed, and runs an HTTPS reverse proxy on `:8443` that exposes only `POST /api/webrtc` (plus the CORS preflight) and the `/api/ws` websocket for configured `src` values with a valid ticket of a non-revoked display; websockets end when their ticket expires. The proxy authenticates to go2rtc with the generated credentials and forwards only the two constant paths. Everything else is 404. TLS certificate and key come from files and are reloaded when they change.
- **Bundle**: `local-services/compose.yaml` with `printer-connector`, `streaming-gateway` and `go2rtc` (go2rtc pinned by tag and digest; connector and gateway by release tag, optional digest variables), an internal network for the go2rtc API, separate outbound networks for connector, gateway and go2rtc, only the gateway's HTTPS port and go2rtc's WebRTC port 8555 (TCP and UDP) published, enrollment secrets from `.env` and the TLS certificate either obtained by the gateway itself (ACME, `ACME_EMAIL` and `CLOUDFLARE_DNS_API_TOKEN`) or taken from an optional read-only `certs/` directory. `streaming-gateway/compose.yaml` is the gateway and go2rtc alone; see [Hosting](hosting.md).
- **Player camera widget** (phase 5b, frontend): WebRTC first, MSE fallback, using the stream URLs and ticket from live data; falls back per widget setting (image / status text / hide) when unavailable.

## Phase 1b decisions

- **Rule concurrency.** Rules have no version of their own: every rule write (create, update, enable toggle, delete, reorder) quotes the display's `expectedVersion` and bumps it. Responses return the full ordered rule list plus the new `displayVersion`. Reorder is `PUT /signage/displays/{id}/rule-order` with the complete id list. New rules are appended; deleting closes position gaps.
- **Pairing details.** The device is created at claim time with an unusable random token digest; the first `paired` poll replaces it with the real token digest (`SetManagedDeviceTokenDigest`) and deletes the request. A claimed request stays collectable for 5 minutes. Poll-secret cookie: `makerspace_signage_pairing` (`__Host-` prefix in production), `Path=/`. Per-IP limit 10 codes/hour, 50 open requests, 10 wrong codes per account per 15 minutes (in-memory, single instance).
- **Managed device type.** Paired devices use a device type named "Signage display", created on demand. Generic managed-device endpoints reject `signage_player` (422) and refuse to edit or rotate signage devices.
- **Manifest response.** `GET /signage/player/manifest` answers `{unchanged, manifest?}` instead of a bare manifest; before the first publication it answers 404 `signage_not_published`. Only enabled rules are published. Pending changes are empty for a display that was never published.
- **Deleting displays.** `DELETE /signage/displays/{id}` (`signage.manage`, `expectedVersion`) works in any state: in one transaction it revokes the managed device if needed, deletes the display with its rules, publications and state, deletes the device, records the display in the streaming revoked list, bumps the session epoch and audits `signage_display.deleted`. The player's next call is rejected (401/404) and it returns to the pairing screen.
- **Revoked displays.** Revoking a display (or its managed device through the generic endpoint) makes the credential invalid (401); a device without a display answers 404.
- **Assets.** Served with HTTP Range support when the storage reader is seekable (local storage); S3 storage streams the full body with `Accept-Ranges: none`.
- **Live.** Open days and events come from the public calendar only (`events.ListUpcomingPublic`: published, planned or confirmed events with a public title, next public session, title/start/location only).

## Media and picker API details

- **Image caps.** PNG, JPEG and WebP up to 20 MiB; at most 8192 px per side and 40 megapixels (422 otherwise). Dimensions come from the decoded header, never from the client.
- **Video.** MP4 only, up to 200 MiB; width, height and duration are optional client-measured headers.
- **File names.** `X-File-Name` carries the percent-encoded UTF-8 name (`encodeURIComponent`). The server decodes it with `url.PathUnescape` and answers 400 `invalid_request` for invalid encodings, invalid UTF-8, control characters or a decoded name over 600 bytes; the stored name is limited to 150 characters (422). Plain ASCII names keep working.
- **Uploader.** Asset responses include `createdByName` (the uploader's person name; `null` once the account is deleted).
- **Content caching.** `GET /signage/assets/{id}/content?v=<sha256>` answers `Cache-Control: private, max-age=31536000, immutable` when `v` equals the asset's `sha256`, and `private, no-store` otherwise. Admin thumbnails and previews always use the `?v=` URL.
- **`GET /signage/machines`.** Picker data for widgets and rules: `{items: [{id, name, kind, hasCamera}]}` ordered by name, `kind` being the machine type. Allowed with `signage.read`, `signage.manage` or `signage.content.manage`; `machines.read` is not needed. `hasCamera` is `true` when the machine has an enabled streaming camera on a non-revoked gateway.
- **Time zone.** `GET /public/config` includes `timeZone`, the makerspace IANA zone the server renders announcements in; the admin announcement preview uses it instead of the browser zone.

## Security hardening (review follow-up)

- **Gateway failure limit** (same limiter, per client IP with IPv6 by /64): 20 failed gateway authentications or enrollments per 15 minutes, then 429 for that address. A gateway with a revoked credential retries and eventually blocks its own address (including other gateways behind it) until the window passes; fix or remove the gateway. Valid gateways are not counted. `HTTP_TRUSTED_PROXIES` applies as for pairing.
- **Pairing rate limits** (in-memory, single instance): 10 codes/hour and 60 polls/minute per client IP (IPv4 by address, IPv6 by /64), 50 open requests, 10 wrong codes per staff account per 15 minutes. The wrong-code counter reserves an attempt before checking the code and refunds it on success, so parallel guesses cannot exceed the limit. Each limiter tracks at most 4096 keys; when full and nothing has expired, new keys are refused (fail closed).
- **Core must see real client addresses.** The production stack trusts its own Compose network (bundled nginx and a host proxy) by default; any other proxy must be listed in `HTTP_TRUSTED_PROXIES`. Otherwise every client appears as the proxy's address and the per-IP limits throttle all displays together.
- **`SIGNAGE_PAIRING_ALLOWED_CIDRS`** (optional, comma-separated CIDRs): when set, `POST /public/signage/pairing` is answered 403 `pairing_network_denied` unless the client IP (after trusted-proxy resolution) is inside one of the networks. Use it to limit pairing to the makerspace LAN. Polling is unaffected.
- **Restarting pairing** never deletes a request staff already claimed; it answers 409 `pairing_claimed` and the player collects its credential with the cookie that started the request (5-minute window).
- **Player rate limits**: 120 requests/minute per device on `/signage/player/*`, 600/minute for asset downloads. `managed_devices.last_seen_at` is written at most every 5 minutes (SQL guard in `TouchManagedDevice`).
- **Uploads**: raw binary upload routes (signage assets, event files, profile images, branding assets, Laborordnung PDFs, connector artifacts) skip OpenAPI request-body validation (headers are still validated), so unauthenticated bodies are never read; size caps remain. Images are limited to 8192 px per side and 40 megapixels. Asset bytes, file row, asset row and both audit events commit in one transaction.
- **Publishing** answers 409 `stale_write` when a concurrent change to the display aborts the snapshot transaction.
- **Announcement retention**: ended announcements are hard-deleted after 30 days, swept from admin reads and (at most every 10 minutes per process) from player live requests.

## Phase 5a decisions (streaming gateway)

- **Public host is set by the administrator** on the gateway (`publicHost`, validated hostname or IPv4 with optional port; no scheme, path, credentials or IPv6 literal). The gateway's `STREAM_PUBLIC_HOST` is only compared with it (warning on mismatch); Core never trusts a value reported by the gateway when building player URLs.
- **Stream names are derived from the machine id** (`cam-<uuid without dashes>`), so they survive gateway re-enrollment and need no storage. The gateway only proxies names present in its configuration, because go2rtc would otherwise treat an arbitrary `src` (an RTSP URL, `exec:`) as a new source.
- **Ticket key storage.** `signage_ticket_keys` holds the Ed25519 seed encrypted with the application keyring (purpose `signage-ticket-key:<id>`). A partial unique index allows one active key; concurrent first-use creation is safe. Without application encryption keys no tickets are issued (streams stay empty) and gateway configuration answers 409 `encryption_not_configured`.
- **Heartbeat health is derived from go2rtc.** go2rtc connects to a printer on the first viewer, so an idle stream is `idle`; `unavailable` means go2rtc is unreachable, the stream is unknown, or viewers exist without a receiving producer. A printer that is switched off therefore shows `idle` until someone watches. go2rtc's `/api/streams` does not report resolution or frame rate (verify on hardware); they stay `null` unless a future go2rtc provides them.
- **Audit.** Gateway and camera mutations, enrollment issue, enrollment, credential rotation and ticket key creation/rotation are audited in the same transaction; secrets, source URLs and tickets never are. Heartbeats and configuration reads are not audited.
- **Admin UI.** Gateways and cameras are administered under Settings, Local services (the key rotation, `POST /local-services/ticket-key/rotation`, stays API-only). The list shows status, version, public host, camera count, enrollment and credential expiry.

## Custom layouts, styling, rich text, lists, agenda and calendar

Decisions of 2026-10-22. Dates on displays stay English (`en-GB`), in the makerspace time zone.

### Custom layouts

- Table `signage_custom_layouts` (migration `00065_signage_custom_layouts.sql`): id, name (1–100, trimmed), mode (`grid`|`free`), columns int[] and rows int[] (grid track weights in `fr`, 1–100 each, 1–12 tracks; free mode stores `{1}`/`{1}`), zones jsonb, created_at, updated_at, version. `signage_scenes` gets `custom_layout_id uuid NULL REFERENCES signage_custom_layouts ON DELETE RESTRICT`, with `CHECK ((layout_id = 'custom') = (custom_layout_id IS NOT NULL))`.
- Zones (1–12, ids `^[a-z][a-z0-9_]{0,39}$`, unique, labels 1–60): `{id, label, grid: {col, row, colSpan, rowSpan} | null, rect: {x, y, width, height} | null}`. Grid mode: every zone has `grid` and no `rect`, lies inside the tracks and zones do not overlap (cells may stay empty). Free mode: every zone has `rect` and no `grid`; values are percentages of the screen with at most two decimals, `width`/`height` ≥ 1, `x + width ≤ 100`, `y + height ≤ 100`; zones may overlap and array order is the stacking order (later on top).
- API (`signage.read` or `signage.content.manage` to read, `signage.content.manage` to write, all audited as `signage_custom_layout.created|updated|deleted` with changed field names): `GET/POST /signage/custom-layouts`, `GET/PUT/DELETE /signage/custom-layouts/{customLayoutId}` (`PUT` and `DELETE` carry `expectedVersion`; 409 `stale_write`). List items carry `sceneCount`. `DELETE` answers 409 `signage_in_use` with `details.references` while a scene uses the layout.
- Removing zones on `PUT` is allowed: in the same transaction every scene using the layout loses the widgets of removed zone ids, gets an empty widget for new zone ids, bumps its version and is audited as `signage_scene.updated` (`zones`). The editor lists the affected scenes before saving.
- Scenes: `layoutId` gains the value `custom`; `customLayoutId` (nullable, required with `custom`, otherwise null) is on `SignageScene`, the create/update requests and `SignagePlayerScene`. Switching between any two layouts keeps widgets by position as before. `SignageZones` allows 12 zones.
- Manifest: `customLayouts: [{id, name, mode, columns, rows, zones, version}]` holds the layouts the published scenes use; `layoutsVersion` is 2. Pending changes gain the kind `layout` (a used custom layout whose version differs from the publication).
- Rendering (`frontend/src/features/signage/layouts.ts` resolves built-in and custom layouts to one shape): grid layouts use CSS grid with `fr` tracks; free layouts position zones absolutely in percent with `z-index` by order.

### Widget style

Every widget (including `empty`, which then works as a coloured box) may carry an optional `style` object; absent means the previous look. All fields are required inside it:
`textColor` / `backgroundColor` / `borderColor` (`#rrggbb` or null), `backgroundOpacity` 0–100, `padding` 0–10 and `radius` 0–10 (in `u`, 1 u = 1 % of the design width), `borderWidth` 0–20 (tenths of `u`), `fontScale` 25–400 (percent), `fontFamily` (`inherit`|`sans`|`serif`|`mono`|`custom`), `fontAssetId` (a font asset, required exactly when `fontFamily` is `custom`), `align` and `verticalAlign` (`inherit`|`start`|`center`|`end`). The style applies to the zone box. The `announcement` widget already uses `style` for its presentation (`banner`, `card`, `full`), so its box style is the field `boxStyle` instead; all other widgets use `style`.

### Fonts

Asset kind `font`: WOFF2 only (`font/woff2`, magic `wOF2`, at most 2 MiB; width, height and duration are null). Fonts reach the manifest through `style.fontAssetId` and through `fontAssetIds` (≤ 10) of rich-text widgets ("fonts used in CSS"); deleting a referenced font is blocked like other assets. The renderer registers each font of a scene once per document with `@font-face { font-family: "<asset name>" }` (name escaped) loaded from the asset URL, so CSS can use the asset name.

### Rich text (markdown and sanitized HTML/CSS, no JavaScript)

- Fields: `format` (`plain`|`markdown`|`html`, absent = `plain`), `css` (≤ 20 000 characters, optional) and `fontAssetIds` on `text`, `open_days`, `events` and `agenda` widgets. Text widgets allow 20 000 characters. Announcement templates get `bodyFormat` (same enum, default `plain`) and `bodyCss` (≤ 20 000); `body` allows 5 000 characters; rendered announcements (`SignageRenderedMessage`, live announcements, admin preview) carry `bodyFormat` and `bodyCss`.
- The browser renders (`frontend/src/features/signage/render/richText.ts`, shared by admin previews and the player): markdown through `marked` (GFM), then markdown and HTML through DOMPurify with scripts, `style` attributes kept, `<style>` elements allowed only in `html`, and `iframe`, `object`, `embed`, `form`, form controls, `link`, `meta`, `base` and event handler attributes removed; URLs only `https:`, `data:image/`, relative and fragments. CSS (the `css` field and `<style>` contents) loses `@import`, `@font-face`, `@namespace`, `expression(`, `behavior:` and `-moz-binding`, and `</style` sequences. The result is placed in a shadow root of the zone, so CSS only affects that box; `var(--u)` is available inside. CSP (`script-src 'self'`) remains the second line of defence.
- The backend validates lengths, enums and references only; it never renders HTML. Plain text stays text nodes.
- Server-side announcement placeholders are escaped for the template's `bodyFormat`: HTML-escaped for `html`, markdown punctuation backslash-escaped and HTML-escaped for `markdown`. The shared vectors in `api/testdata/signage-announcement-render.json` cover all three formats.

### Open day, event and agenda lists

- `open_days` and `events` widgets: `count` 1–20 and optional `title` (≤ 200; absent = the previous heading, empty = no heading), `emptyText` (≤ 500), `entryTemplate` (≤ 5 000) plus the rich-text fields. One template is rendered per entry; an empty or absent template keeps the previous row layout. The whole list is one rich-text document, each entry wrapped in `<div class="entry entry--open_day|entry--event">`, so the CSS styles all entries alike.
- New `agenda` widget: open days and events merged by start time: `count` 1–20, `includeOpenDays`, `includeEvents`, `title`, `emptyText`, `openDayTemplate`, `eventTemplate`, rich-text fields, `style`.
- Placeholders `{name}`, values escaped for the format: `{kind}` (`Open day`/`Event`), `{title}` (`Open day` for open days), `{date}` (`Thu 23 Oct`), `{weekday}`, `{weekday_short}`, `{day}`, `{month}`, `{month_short}`, `{year}`, `{start}`, `{end}` (`HH:MM`; empty when unknown), `{status}` (open days: `Scheduled`/`Cancelled`), `{location}` (events; empty when none), `{competencies}` (open days: the planned competencies, comma-separated; empty when none). Unknown placeholders stay as written.
- `open_days` and `agenda` widgets: optional `showCompetencies` (absent = false) adds the planned competencies as outlined chips below the standard open-day row, the first four and `+n`. Templates use `{competencies}` instead. Events widgets reject the field.
- Live data: `openDays` and `events` hold up to 20 entries (`liveListLimit` 20); events gain `endsAt` (nullable). `GET /signage/calendar` follows.

### Calendar widget

- Widget `calendar`: `view` (`month`|`weeks`), `weeks` 1–6 (weeks view, starting with the current ISO week), `showHolidays`, `showBreaks`, `showOpenDays`, `showEvents`, `colors: {holiday, break, openDay, event}` (`#rrggbb`), `showWeekNumbers`, `title` (≤ 200, empty hides), `style`, optional `showCompetencies` (absent = false: in the weeks view open days show their first two planned competencies and `+n`; month cells are too small and cancelled days show none). Weeks start on Monday.
- Live data: `SignagePlayerLive.calendar` (nullable) is present only while the display's publication contains a calendar widget and holds only the categories some published calendar widget shows: `{from, to, holidays: [{date, name}] (≤ 60), breaks: [{name, startsOn, endsOn}] (≤ 20), openDays (≤ 100), events (≤ 100)}`. The range runs from 7 days before the first day of the current month to 49 days after today (makerspace time zone, dates inclusive). Holidays come from the Open Days holiday provider, breaks from `open_day_academic_breaks` (overlapping the range), open days only from published periods and events only from the public calendar, including past entries inside the range. `GET /signage/calendar` returns the same `calendar` block with every category for admin previews.
- The player persists the calendar like open days and events.

## Hiding a run from signage

A person can opt a run out of digital signage (`PUT /machine-runs/{runId}/signage-visibility`, `hiddenFromSignage` on the run, migration `00067`). While a run with the flag is running (a recorded run in state `running`, a manual run before its planned end), its machine is hidden from signage entirely: it is missing from `machines` of `/signage/player/live` and of the admin preview, no stream ticket is issued for its camera, and automatic camera widgets skip it. The check runs on every live poll (`ListSignageHiddenMachineIDs`), so the machine reappears on its own when the run ends; the flag belongs to the run, so the next run starts visible. The machine picker in the admin UI is unchanged.

Stream tickets are signed and verified offline by the streaming gateway, so a ticket issued shortly before the opt-out keeps working until it expires (five minutes at most). The player stops requesting the camera as soon as its next live poll no longer lists the stream.
