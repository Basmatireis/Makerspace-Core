# Digital signage

Centrally managed information and advertising screens for one makerspace. Displays run a small, separate player web app in a Chromium kiosk. Content, rules and devices are managed in Core; printer camera video is relayed by Core from the makerspace's local service to the displays, over the displays' own connection to Core.

This document is the implementation contract for digital signage.

## Concepts

| Concept               | Meaning                                                                                                                                                    |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Display               | One physical screen with an aspect ratio, bound 1:1 to a managed device whose only application mode is `signage_player`; optionally a member of one group. |
| Scene (UI: Screen)    | One screen composition: freely positioned **blocks** (each one widget with a box style), background colour/image, text theme. The UI says "Screen".       |
| Display group         | Displays with one aspect ratio that show the same thing: the group owns the rules and the default scene list; publishing the group publishes every member. |
| Rule                  | Per display or group, ordered. "When _condition_ show _scene list_". First enabled match wins; the default scene list is the fallback.                     |
| Publication           | Immutable manifest per display: rules, default scene list and every scene and asset they reach, at publish time. Players only ever play publications.      |
| Asset                 | An uploaded image or video (metadata here, bytes in the existing files/storage module).                                                                    |
| Announcement template | Fields (typed inputs) + title/body with `{placeholders}` + tone.                                                                                           |
| Announcement          | A started instance of a template: values, target displays (all or selected), start, optional end. Live data, never published.                              |

## Permissions (registered; never role names)

| Permission               | Allows                                                                                                          |
| ------------------------ | --------------------------------------------------------------------------------------------------------------- |
| `signage.read`           | Read displays, health, content, media, rules, announcements                                                     |
| `signage.manage`         | Pair, rename, revoke, delete displays; manage display groups; edit rules, default scene lists, display settings |
| `signage.content.manage` | Create/edit/duplicate/delete scenes, assets and announcement templates                                          |
| `signage.publish`        | Publish a display                                                                                               |
| `signage.override`       | Start, edit, stop announcements                                                                                 |

Every write permission implies nothing else; services check exactly what they need and the frontend hides controls accordingly (UX only).

## Data model (migrations `00051_signage.sql`, `00052_signage_player_mode.sql`; reworked by `00090`–`00093`)

UUIDv7 ids generated in Go, `timestamptz` UTC, `version int` for optimistic concurrency on editable rows (`expectedVersion` on writes, 409 `stale_write`). JSONB only for the scene blocks and publication manifests.

- `signage_displays`: id, managed_device_id (unique, FK managed_devices ON DELETE RESTRICT), name, location, aspect_width/aspect_height (smallint, reduced), group_id (nullable FK `signage_display_groups`, RESTRICT), visible_from_outside bool, revoked_at, created_at, updated_at, version.
- `signage_pairing_requests`: id, code_digest (unique among open requests), poll_secret_digest, created_at, expires_at (15 min), claimed_display_id (nullable FK), claimed_at, delivered_at. Rows are deleted after delivery or expiry (cleanup on access + periodic sweep is not needed; delete expired rows opportunistically in the same statements).
- `signage_assets`: id, file_id (FK files, RESTRICT), kind (`image`|`video`), name, width, height, duration_ms (nullable), created_by_account_id, created_at.
- `signage_scenes`: id, name, aspect_width/aspect_height, background_color (`#rrggbb`), background_asset_id (nullable FK RESTRICT), background_fit (`cover`|`contain`), background_dim (0–80), theme (`dark`|`light`), font_family (`sans`|`serif`|`mono`|`custom`), font_asset_id (nullable FK RESTRICT), blocks jsonb (array), created_at, updated_at, version.
- `signage_display_groups`: id, name, aspect_width/aspect_height, created_at, updated_at, version. Groups own rules and a default scene list (see [Display groups](#display-groups)).
- `signage_rules`: id, display_id or group_id (exactly one set, FK CASCADE), position, enabled, condition_kind (`time_window`|`machine_printing`|`announcement_active`|`live_data_unavailable`), weekdays smallint[] (ISO 1–7), time_from/time_to (time, may wrap midnight), machine_ids uuid[], machine_match (`any`|`all`), announcement_template_ids uuid[] (empty = any), min_seconds (0–600, default 20), multi_mode (`split`|`alternate`), alternate_seconds. CHECK constraints per kind. Unique (display_id, position) and (group_id, position), DEFERRABLE.
- `signage_rule_scenes`: rule_id (FK CASCADE), position, scene_id (FK RESTRICT), seconds (3–3600), transition (`cut`|`fade`); the scene list a rule shows. `signage_default_scenes`: the same for the default scene list of a display or group (display_id or group_id, exactly one).
- `signage_publications`: id, display_id (FK CASCADE), revision (per display, starting 1), manifest jsonb, manifest_sha256, published_by_account_id, published_at. Unique (display_id, revision). Keep the latest 5 per display.
- `signage_display_states` (ephemeral, not audited): display_id PK, last_heartbeat_at, publication_revision, current_rule (text: rule id, `default`), current_scene_id, player_version, cache_used_bytes, cache_quota_bytes, errors jsonb (max 20 short entries, no PII).
- `signage_announcement_templates`: id, name, tone (`info`|`warning`|`critical`|`neutral`), title, body, created_at, updated_at, version. `signage_announcement_template_fields`: template_id, position, key (`^[a-z][a-z0-9_]{0,39}$`, not a built-in), label, type (`text`|`longtext`|`time`|`date`|`datetime`|`number`|`choice`|`machine`), required, default_value, helper_text, options text[] (choice only).
- `signage_announcements`: id, template_id (FK RESTRICT), all_displays bool, starts_at, ends_at (nullable), created_by_account_id, created_at, updated_at, version. `signage_announcement_values`: announcement_id, key, value (text ≤ 2000). `signage_announcement_displays`: announcement_id, display_id. `signage_announcement_groups`: announcement_id, group_id. Ended announcements are hard-deleted after 30 days (on access) — no indefinite retention of message content.
- Cameras (migration `00084_unified_local_service.sql`): the gateway tables of `00053`, `signage_ticket_keys`, `signage_revoked_displays` and `streaming_session_epoch` are gone. A camera is the boolean `camera_streaming` on an active Bambu printer-connector assignment (plus ephemeral `camera_health`, `camera_viewers`, `camera_reported_at` from the connector's heartbeat). `signage_displays.allow_camera_outside` stays. Camera RTSPS host and access code are **not** duplicated: the connector renders them from the assignment's settings and encrypted secrets.

Every mutation writes its audit event in the same transaction (`audit.Write`, changed field names only; never announcement values or token material). Pairing, heartbeats and live reads are not audited, except pairing claim and device revoke.

## Scene blocks (JSONB, validated in Go)

Since migration `00129_signage_scene_blocks.sql` a scene is a list of freely positioned **blocks** (`signage_scenes.blocks`, a JSON array, at most 40, at most 1 MiB); built-in and custom layouts are gone. A scene is laid out on a grid whose short side is 1080 units: landscape and square scenes are `round(1080 · w / h) × 1080`, portrait scenes `1080 × round(1080 · h / w)`. Renderers draw the scene at exactly that size and scale the whole picture with `transform: scale()` to the box (`SceneRenderer`), so text wraps the same at every size and previews and displays look the same. The scene root resets typography (font, size, weight, style, spacing, smoothing), so page styles such as Carbon never leak into previews.

A block (`SignageBlock`, strictly decoded) has `id` (`^[A-Za-z0-9_-]{1,40}$`, unique in the scene), `name` (1–60), integer `x`/`y` (−120000…120000) and `w`/`h` (8…120000) in grid units, `hidden` (not shown on displays; its widgets reach no manifest asset, machine, camera, calendar or timelapse list), `locked` (editor only), one `widget` and a `style`. Array order is the stacking order (later on top). Widget types and fields are defined in `api/openapi.yaml` (`empty`, `image`, `video`, `slideshow`, `text`, `qr`, `clock`, `camera`, `status`, `open_days`, `events`, `announcement`, `agenda`, `calendar`, `timelapse`); unknown keys are rejected, text lengths are capped, QR URLs must be `https://`. Widgets carry no style of their own: `text` has `text`, rich text fields and `fit` (shrink to fit, renderer-side) but no `size`/`align`; `announcement` has no `size`; `camera` has `showLive` and `showName`; `image` has `dim` (0–90 %).

`SignageBlockStyle` has every field required: `backgroundColor` (`#rrggbb` or null) and `backgroundOpacity` 0–100, `backgroundAssetId` (image asset or null) and `backgroundDim` 0–90 (both must be null/0 for the media widgets image, video, slideshow, camera and timelapse), `textColor` (null = scene default), `borderWidth` 0–40, `borderStyle` (`solid`|`dashed`|`dotted`|`double`), `borderColor` (null = current colour), `radius` 0–400, `shadow` (`none`|`soft`|`strong`|`glow`), `fontFamily` (`inherit`|`sans`|`serif`|`mono`|`custom`) with `fontAssetId` exactly when `custom`, `fontWeight` (`inherit`|`400`|`500`|`600`|`700`), `lineHeight` 80–250 (percent), `letterSpacing` −10…50 (hundredths of an em), `uppercase`, `textSize` 8–400, `padding` 0–400, `align` and `verticalAlign` (`start`|`center`|`end`), `opacity` 10–100. `textSize` is the font size of text widgets and of the announcement title (the body is 0.6 of it); every other widget scales its internal sizes with it, 32 being the default look (`--u = 10.8px · textSize / 32`; for text and announcement blocks, whose `textSize` is a font size, `--u = 10.8px · textSize / 50`, so the former default size keeps its paddings; `blockUnit` in `render/style.ts`). A scene has its own font (`fontFamily`, `fontAssetId`) that blocks with font `inherit` use.

### Conversion of layouts and zones (migration 00129, manifest version 4)

Migration 00129 converts every stored scene in PL/pgSQL; `backend/internal/signage/convert.go` (`ConvertLegacyScene`) applies the same rules to publications stored before it, and `TestSignageBlocksMigrationMatchesGoConversion` keeps both identical. Scene versions are kept, so no display reports a pending change. The old unit `u` was 1 % of the short side, i.e. 10.8 grid units; all arithmetic is integer with half-up rounding.

- Geometry: each zone of the scene's layout becomes one block in layout order (free layouts: array order), empty and missing zones included, with the zone id as block id and the label as name. Grid layouts (the nine built-in ones and custom grids) compute track lines `round(size · cumulative weight / total weight)` so blocks tile without gaps; free layouts round both edges of each percent rectangle. A missing custom layout or an unknown layout id renders as `full`.
- Style: colours, background opacity and custom font move over; padding and radius × 10.8, border width (tenths of u) × 1.08. Without a zone style, text, status, clock, open days, events, agenda, calendar and QR blocks get the old 2u padding (22), others 0; a zone style always replaced it.
- `textSize`: text and announcement `round(s 3 / m 4.6 / l 7 / xl 10 × 10.8 × fontScale / 100)` (32, 50, 76, 108 at 100 %, at most 400); every other widget `round(32 × fontScale / 100)`.
- Alignment: clocks, QR codes and full-screen announcements are centred (they ignored the style); otherwise the zone style's alignment, else the text widget's own `align`, else start. Vertical alignment is the zone style's, else centre for text, clock, QR, status, announcement and camera, else start.
- Typography: plain text gets weight 600 and line height 115, rich text line height 130, announcements 115, everything else 125; letter spacing 0, no uppercase, no shadow, solid border, opacity 100.
- Widgets: `style`/`boxStyle` removed; text loses `size` and `align` and gets `fit: false`; announcements lose `size`; cameras get `showLive` and `showName` true; images get `dim` 0.
- Down is lossy: every scene gets the full layout with the widget of its first visible non-empty block (text and announcement size from the nearest old size), and the custom layouts table comes back empty.

## Publish and drafts

Scenes, rules, default scene lists, group membership and display settings are drafts. `POST /signage/displays/{id}/publish` (signage.publish) builds the manifest (`manifestVersion: 4`) from current drafts in one transaction, stores the publication and audits it; for a display in a group the content is the group's. `POST /signage/groups/{groupId}/publish` publishes every member in one transaction. `GET /signage/displays/{id}` returns `publishedRevision`, `publishedAt` and `pendingChanges: [{kind, name, change}]` (kinds `display`, `rule`, `scene`, `asset`; a changed default scene list is `display` named `Default scenes`), computed by comparing the draft manifest with the latest publication (by entity id + version). Deleting a scene/asset referenced by drafts is a 409 listing references; anything only referenced by older publications may be deleted (players keep their cached copy until they get a new manifest).

## Player protocol

The player is unauthenticated until paired, then authenticates as its managed device (HttpOnly cookie, the existing managed-device cookie). A `signage_player` device may only call `/signage/player/*` (and the public pairing endpoints); it can never hold a staff session. All player responses are `Cache-Control: no-store` except content-addressed asset bytes.

1. **Pairing.** `POST /public/signage/pairing` → creates a request with a 6-character code from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (CSPRNG) and a 32-byte poll secret set as HttpOnly `SameSite=Strict` cookie; returns `{code, expiresAt}`. Rate-limited per client IP (e.g. 10/hour) and globally capped (e.g. 50 open requests). `GET /public/signage/pairing` (poll every 3 s, with that cookie) → `pending` | `expired` | `paired`. On the first `paired` poll the server creates the device token, sets the managed-device cookie, marks the request delivered and deletes it — the plaintext token never sits in the DB.
   Staff: `POST /signage/displays` `{code, name, location, aspectRatio, visibleFromOutside, allowCameraOutside?, defaultScenes, groupId?}` (signage.manage) finds the open request by code digest, creates managed device (mode `signage_player`, no staff, no kiosk), display and an empty first publication-ready state; unknown/expired code → 422 `pairing_code_invalid` (same message for both). Failed attempts are rate-limited per account.
2. **Manifest.** `GET /signage/player/manifest?known=<revision>` → 304-like `{unchanged: true}` or the full manifest `{manifestVersion, revision, display: {aspectRatio, visibleFromOutside}, rules, defaultScenes, scenes, assets: [{id, kind, sha256, size, url}]}` (`manifestVersion` 4; scenes carry `blocks`; a cached manifest below 4 is refetched, see [Player app](#player-app)); every rule carries its `scenes` list. Assets: `GET /signage/player/assets/{assetId}/{sha256}` → bytes, `Cache-Control: private, max-age=31536000, immutable`, only if the asset is in the display's latest publication.
3. **Live.** `GET /signage/player/live` every ~10 s → `{serverTime, revision, machines: [{machineId, name, state, progressPercent, remainingMinutes, observedAt, stale}], announcements: [{id, templateId, tone, title, body, startsAt, endsAt}], openDays: [...next 5 public: startsAt, endsAt, status, competencies (public labels only)], events: [...next 5 public-safe: title, startsAt, location], streams: [{machineId, path}], timelapses: [{runId, machineId, machineName, endedAt, sha256, sizeBytes, url}] | null, calendar }`; `timelapses` is present only while the publication contains a timelapse widget (see [Timelapse widget](#timelapse-widget)). Machines are those referenced by the display's published rules/widgets; state comes from `printer_live_statuses`, stale when `received_at` is older than 3 minutes (state `unknown`). Announcements are rendered server-side (Go is authoritative; built-ins `{ends_at} {ends_on} {ends} {starts_at} {today} {display} {location}`; times in the makerspace time zone from config). No customer data, ever.
4. **Heartbeat.** `POST /signage/player/heartbeat` `{revision, currentRule, currentSceneId, playerVersion, cacheUsedBytes, cacheQuotaBytes, errors[]}` every 30 s → upserts `signage_display_states`. Display status: online if heartbeat < 90 s, otherwise offline.

The player evaluates rules locally (TypeScript engine shared with the admin preview: `frontend/src/features/signage/engine/`), so time windows keep working offline. `live_data_unavailable` matches when the last successful live poll is older than 60 s. Min display time is enforced by the player (a winning rule keeps the screen for at least `min_seconds` unless a higher-priority rule takes over). Announcement rendering also has a TypeScript copy for the admin live preview; both implementations run the same JSON test vectors (`api/testdata/signage-announcement-render.json`).

## Player app

Separate Vite entry `frontend/player.html` → `src/player/main.tsx`; no Carbon, no TanStack Query, no app shell; plain CSS. It must not import from `src/app` or Carbon packages (lint rule or test). Its own bundle budget: ≤ 90 kB gzip JS, ≤ 20 kB CSS; the service worker ≤ 4 kB gzip. Served by the same nginx at `/player/` with `Cache-Control: no-cache` for HTML.

- Screens: pairing code (a lazy chunk, so a paired display never loads it) (big code, expiry countdown, regenerates on expiry), playing, fatal error.
- Offline (phase 4): a service worker (`src/player/sw.ts`, built to `/player/sw.js`, scope `/player/`, served `no-cache`) precaches the player shell (`/player/` plus the hashed JS/CSS of the player entry; the build fills the file list in from the Vite manifest) and answers `/api/v1/signage/player/assets/{id}/{sha256}` from Cache Storage (including byte ranges for videos). The runtime downloads every asset of a new manifest into the `signage-assets-v1` cache, keyed by the asset's player URL path, which embeds the sha256, and saves the manifest to `signage-state-v1`; only then does the revision activate. After activation, assets the active manifest does not reference are evicted. A cold start restores the persisted manifest (when all its assets are cached) and plays it without network; a network error never shows the pairing screen, only a 401/403 (or an unknown 404) does and then clears the cache. The player asks for persistent storage and reports `navigator.storage.estimate()` as `cacheUsedBytes`/`cacheQuotaBytes` in heartbeats; a revision whose missing assets exceed the free quota (or whose download hits `QuotaExceededError`) is refused, the old one keeps playing and the error is reported. Without Cache Storage (insecure origin) the player falls back to in-memory preloading. Timelapse clips listed in the live payload are cached the same way in `signage-timelapses-v1` (see [Timelapse widget](#timelapse-widget)). Only published content is stored: manifest, assets and the announcements/open days/events of the last live payload, never credentials or machine status.
- Live data lifetime: machine status shows "Status unknown" (and `live_data_unavailable` applies) after 60 s without a successful poll; machines are never restored from storage. Announcements are kept until their `endsAt`, open-ended ones until the next successful poll. Announcements, open days and events are persisted with a timestamp (rewritten when they change, otherwise every 5 minutes) and restored after a restart if younger than 24 h.
- Start order: the player asks for the manifest first. Live polling and heartbeats start only after that call was answered by the server with an authenticated response (or after a revision was restored from the cache), so an unpaired display makes no 401 requests besides the manifest call that sends it to pairing.
- Implemented in `frontend/src/player/`: `api.ts` (five-call fetch wrapper), `pairing.ts` (pairing loop), `runtime.ts` (revision activation after preload, live/heartbeat/manifest loops, backoff, revocation), `view.ts` (shared engine plus the `min_seconds` hold), `camera.ts` (`CameraSource` seam: `hasStream` marks cameras without a stream unavailable, `view` supplies the picture through `RenderData.cameraView`), `lazyCamera.ts`, `cameraManager.tsx` and `stream.ts` (camera websocket, loaded as a lazy chunk on the first camera widget, see [Cameras](#cameras-relayed-by-core)). The import graph is enforced by an ESLint override and `src/player/imports.test.ts`; the budget (JS 90 kB, CSS 20 kB gzip) is checked per entry in `scripts/check-bundle-budget.mjs`. A 404 other than `signage_not_published` on a player endpoint is treated like a revoked credential.
- Lazy chunks keep the entry inside the budget: the camera manager, QR codes, the open-day/event/agenda lists, the calendar, the timelapse widget and the pairing screen load only when a published scene or the pairing state needs them; the timelapse cache (`timelapseCache.ts`) loads on the first live payload that lists clips.
- Fonts: the player bundles the IBM Plex Sans, Serif and Mono woff2 files its CSS names (`player.css`, `@font-face`); the build lists the assets of the player CSS in the shell files, so the service worker precaches them and a display that starts offline still renders the default fonts.
- Manifest version: `MANIFEST_VERSION` is 4 (blocks). A manifest cached before (below 4, or without the field) is discarded on start and refetched; a network error then shows the waiting screen, not pairing.
- Kiosk: documented Chromium flags and a systemd unit example in `docs/signage-player.md` (autostart, watchdog restart, screen blanking off).

## Cameras relayed by Core

Printer cameras need no extra server and no extra network path for the displays: the video travels printer, go2rtc, printer connector, Core, display, and every hop is an outbound connection toward Core or the display's own connection to Core. Setup, ports and the go2rtc security model are in [Printer connector](printer-connector.md#camera-streaming); this section is the signage side.

- **Who may watch.** A paired, non-revoked signage player (managed-device cookie or token) may watch a machine's camera exactly while the display's latest **publication** contains a camera widget that covers that machine (a `machine` widget names it; an `auto` widget covers every machine it may show, optionally limited by `machineIds`), the machine has an active Bambu printer-connector assignment with the camera switch on, and the machine is not hidden from signage by a running run (see [Hiding a run from signage](#hiding-a-run-from-signage)). **Displays visible from outside** (`visibleFromOutside`) may only watch when the display setting `allowCameraOutside` (default off, audited as a changed field, stored either way, takes effect immediately without a publication) is on. The display detail page warns ("Live cameras are not shown") while such a display's current publication contains a camera widget, because those widgets then only show their fallback. The staff preview (`GET /signage/displays/{id}/preview`) never carries streams.
- **Live data.** `GET /signage/player/live` lists `streams: [{machineId, path}]` for the cameras the display may watch right now (at most 20). `path` is the relative URL `/api/v1/signage/player/cameras/{machineId}/stream`; there is no host, ticket or token in it. A camera disappears from the list on the next poll (at most ~10 s) after the machine is hidden, the switch is turned off, the display is republished without the camera or `allowCameraOutside` is switched off.
- **Viewer websocket.** The player opens `wss://<its own origin><path>`. Authentication is the display's managed-device cookie (or the token header, which may omit `Origin`); browser upgrades must carry an `Origin` equal to the application's public origin. Errors before the upgrade: 401, 403 (not allowed to watch), 404 (unknown machine or no streaming camera), 409 `camera_offline` (the connector has no open control channel), 429 (limits) and 503 (the connector did not answer within 10 s). After the upgrade the player sends one text frame `{"type":"mse","value":"<codecs>"}` (the go2rtc MSE protocol) and receives text and binary frames; Core is a byte pipe and parses no media. Viewer frames are limited to text, 4 KiB and 10 per second (a binary frame ends the session); frames from the connector may be up to 4 MiB.
- **Limits.** At most 4 concurrent streams per device and machine and 20 per device in total; 32 concurrent sessions per connector. go2rtc fans out locally, so several displays on one camera cost the printer a single RTSP connection.
- **Re-authorization and close codes.** Core re-checks the right to watch every 15 seconds (device still paired, scene still containing the camera, assignment active with the switch on, connector active). The viewer socket closes with **4403** (forbidden), **4404** (camera gone) or **4503** (connector offline). The player stops and shows the fallback on 4403/4404 until the next live poll lists the stream again; on 4503 and other closes it retries with backoff.
- **Latency and live edge.** The player uses Media Source Extensions only (no WebRTC); expect about 1 to 2 seconds of latency. When the playback buffer lags more than 3 seconds behind the live edge the player jumps forward to it, so a display that was throttled in the background catches up instead of drifting.
- **Session lifetime and revocation.** Sessions are checked by Core itself every 15 seconds, so revoking or deleting a display, republishing without the camera or switching `allowCameraOutside` off ends running sessions within about 15 seconds; there are no tickets that could outlive a decision. Deleting a display ends its camera sessions immediately.
- **Camera switch and health.** The camera is a switch (`cameraStreaming`) on a Bambu printer-connector assignment, changed with the assignment (`printer_connectors.manage`; 422 for other adapters) and carried in the audit event of that update. The connector reports `live`, `idle` or `unavailable` and the viewer count per camera in its heartbeat (stored ephemerally, not audited); Core shows `unknown` when the connector never reported or its last report is older than two minutes. An idle stream means go2rtc is configured but nobody watches: go2rtc connects to the printer on the first viewer.
- **Player camera widget.** Plays the stream through the shared player camera manager; falls back per widget setting (image / status text / hide) when unavailable or while connecting.
- **Core requirements.** The relay needs the Core reverse proxy to pass websockets for the viewer path and the connector paths ([Hosting](hosting.md#reverse-proxy-and-websockets)); the player CSP allows `connect-src 'self'` only, which covers the same-origin websocket.

## Admin UI (real app)

`frontend/src/features/signage/`, routes lazy-loaded, nav group "Signage" (Displays with a Groups section, Announcements, Screens, Media) and "Local services" under the existing settings area. Carbon components only; React Hook Form for the pair, rule, template and announcement forms; TanStack Query for server state. The scene renderer is shared between admin previews and the player (`src/features/signage/render/`, plain CSS, no Carbon) so previews are pixel-equivalent. The Displays page lists displays and groups (group page `/signage/groups/{id}` with Playback, Members and Settings tabs; the display page shows "Managed by group …" and the group's rules read-only while the display is in a group). The Screens page (`/signage/content`) lists screens and announcement templates (no playlists, no layouts) with a "Duplicate" row action; a screen opens in the editor (`src/features/signage/editor/`: canvas with snapping, palette, blocks list, toolbars, properties panels for a block, several blocks and the screen, preview and publish dialogs). Pickers for image and video widgets and backgrounds can upload a file in place (`MediaPicker`, `assetUpload.ts`, same caps as the Media page). Rules and default scene lists are edited as ordered lists of scenes with seconds and transition. The screen editor autosaves drafts and has Undo and Redo, no Save or Discard (see [Scene editor](#scene-editor-autosave-undo-and-redo)).

## Phase 1b decisions

- **Rule concurrency.** Rules have no version of their own: every rule write (create, update, enable toggle, delete, reorder) quotes the `expectedVersion` of the owner (display or group) and bumps it. Responses return the full ordered rule list plus the new `ownerVersion`. Reorder is `PUT /signage/displays/{id}/rule-order` with the complete id list. New rules are appended; deleting closes position gaps.
- **Pairing details.** The pairing request carries `code`, `name`, `location`, `aspectRatio`, `visibleFromOutside`, `defaultScenes` and an optional `groupId`. The device is created at claim time with an unusable random token digest; the first `paired` poll replaces it with the real token digest (`SetManagedDeviceTokenDigest`) and deletes the request. A claimed request stays collectable for 5 minutes. Poll-secret cookie: `makerspace_signage_pairing` (`__Host-` prefix in production), `Path=/`. Per-IP limit 10 codes/hour, 50 open requests, 10 wrong codes per account per 15 minutes (in-memory, single instance).
- **Managed device type.** Paired devices use a device type named "Signage display", created on demand. Generic managed-device endpoints reject `signage_player` (422) and refuse to edit or rotate signage devices.
- **Manifest response.** `GET /signage/player/manifest` answers `{unchanged, manifest?}` instead of a bare manifest (the manifest is upgraded in memory when the stored publication predates `manifestVersion` 4); before the first publication it answers 404 `signage_not_published`. Only enabled rules are published; rules of a group display are the group's. Pending changes are empty for a display that was never published.
- **Deleting displays.** `DELETE /signage/displays/{id}` (`signage.manage`, `expectedVersion`) works in any state: in one transaction it revokes the managed device if needed, deletes the display with its rules, publications and state, deletes the device, ends its camera sessions and audits `signage_display.deleted`. The player's next call is rejected (401/404) and it returns to the pairing screen.
- **Revoked displays.** Revoking a display (or its managed device through the generic endpoint) makes the credential invalid (401); a device without a display answers 404.
- **Assets.** Served with HTTP Range support when the storage reader is seekable (local storage); S3 storage streams the full body with `Accept-Ranges: none`.
- **Live.** Open days and events come from the public calendar only (`events.ListUpcomingPublic`: published, planned or confirmed events with a public title, next public session, title/start/location only).

## Media and picker API details

The search on the Media page matches the file name, the type label (Image, Video, Font) and the content type (for example `image/png`).

- **Image caps.** PNG, JPEG and WebP up to 20 MiB; at most 8192 px per side and 40 megapixels (422 otherwise). Dimensions come from the decoded header, never from the client.
- **Video.** MP4 only, up to 200 MiB; width, height and duration are optional client-measured headers.
- **File names.** `X-File-Name` carries the percent-encoded UTF-8 name (`encodeURIComponent`). The server decodes it with `url.PathUnescape` and answers 400 `invalid_request` for invalid encodings, invalid UTF-8, control characters or a decoded name over 600 bytes; the stored name is limited to 150 characters (422). Plain ASCII names keep working.
- **Uploader.** Asset responses include `createdByName` (the uploader's person name; `null` once the account is deleted).
- **Content caching.** `GET /signage/assets/{id}/content?v=<sha256>` answers `Cache-Control: private, max-age=31536000, immutable` when `v` equals the asset's `sha256`, and `private, no-store` otherwise. Admin thumbnails and previews always use the `?v=` URL.
- **`GET /signage/machines`.** Picker data for widgets and rules: `{items: [{id, name, kind, hasCamera}]}` ordered by name, `kind` being the name of the machine's process. Allowed with `signage.read`, `signage.manage` or `signage.content.manage`; `machines.read` is not needed. `hasCamera` is `true` when the machine has an active Bambu printer-connector assignment with camera streaming switched on.
- **Time zone.** `GET /public/config` includes `timeZone`, the makerspace IANA zone the server renders announcements in; the admin announcement preview uses it instead of the browser zone.

## Security hardening (review follow-up)

- **Pairing rate limits** (in-memory, single instance): 10 codes/hour and 60 polls/minute per client IP (IPv4 by address, IPv6 by /64), 50 open requests, 10 wrong codes per staff account per 15 minutes. The wrong-code counter reserves an attempt before checking the code and refunds it on success, so parallel guesses cannot exceed the limit. Each limiter tracks at most 4096 keys; when full and nothing has expired, new keys are refused (fail closed).
- **Core must see real client addresses.** The production stack trusts its own Compose network (bundled nginx and a host proxy) by default; any other proxy must be listed in `HTTP_TRUSTED_PROXIES`. Otherwise every client appears as the proxy's address and the per-IP limits throttle all displays together.
- **`SIGNAGE_PAIRING_ALLOWED_CIDRS`** (optional, comma-separated CIDRs): when set, `POST /public/signage/pairing` is answered 403 `pairing_network_denied` unless the client IP (after trusted-proxy resolution) is inside one of the networks. Use it to limit pairing to the makerspace LAN. Polling is unaffected.
- **Restarting pairing** never deletes a request staff already claimed; it answers 409 `pairing_claimed` and the player collects its credential with the cookie that started the request (5-minute window).
- **Player rate limits**: 120 requests/minute per device on `/signage/player/*`, 600/minute for asset downloads. `managed_devices.last_seen_at` is written at most every 5 minutes (SQL guard in `TouchManagedDevice`).
- **Uploads**: raw binary upload routes (signage assets, event files, profile images, branding assets, Laborordnung PDFs, connector artifacts) skip OpenAPI request-body validation (headers are still validated), so unauthenticated bodies are never read; size caps remain. Images are limited to 8192 px per side and 40 megapixels. Asset bytes, file row, asset row and both audit events commit in one transaction.
- **Publishing** answers 409 `stale_write` when a concurrent change to the display aborts the snapshot transaction.
- **Announcement retention**: ended announcements are hard-deleted after 30 days, swept from admin reads and (at most every 10 minutes per process) from player live requests.

## Camera decisions

- **Stream names are derived from the assignment id** (`cam-<assignmentId>`), so they need no storage and survive connector re-enrollment. The connector only serves names present in its current configuration, because go2rtc would otherwise treat an arbitrary `src` (an RTSP URL, `exec:`) as a new source.
- **Heartbeat health is derived from go2rtc.** go2rtc connects to a printer on the first viewer, so an idle stream is `idle`; `unavailable` means go2rtc is unreachable, the stream is unknown, or viewers exist without a receiving producer. A printer that is switched off therefore shows `idle` until someone watches. go2rtc's `/api/streams` does not report resolution or frame rate (verify on hardware).
- **Audit.** Changing the camera switch is part of the assignment update's audit event in the same transaction; secrets and source URLs never are. Heartbeats, configuration reads and relay sessions are not audited (sessions are logged with machine id, device id, duration and bytes only).
- **Admin UI.** The switch is a Carbon `Toggle` "Stream camera" in the printer setup of a Bambu assignment; the connectors tab shows the camera health as a tag. Permission: `printer_connectors.manage`.

## Styling, fonts, rich text, lists, agenda and calendar

Decisions of 2026-10-22. Dates on displays stay English (`en-GB`), in the makerspace time zone.

### Widget style

Replaced by the block style (see Scene blocks); migration 00129 converted every widget style.

### Fonts

Asset kind `font`: WOFF2 only (`font/woff2`, magic `wOF2`, at most 2 MiB; width, height and duration are null). Fonts reach the manifest through the block style's `fontAssetId` and through `fontAssetIds` (≤ 10) of rich-text widgets ("fonts used in CSS"); deleting a referenced font is blocked like other assets. The renderer registers each font of a scene once per document with `@font-face { font-family: "<asset name>" }` (name escaped) loaded from the asset URL, so CSS can use the asset name.

### Rich text (markdown and sanitized HTML/CSS, no JavaScript)

- Fields: `format` (`plain`|`markdown`|`html`, absent = `plain`), `css` (≤ 20 000 characters, optional) and `fontAssetIds` on `text`, `open_days`, `events` and `agenda` widgets. Text widgets allow 20 000 characters. Announcement templates get `bodyFormat` (same enum, default `plain`) and `bodyCss` (≤ 20 000); `body` allows 5 000 characters; rendered announcements (`SignageRenderedMessage`, live announcements, admin preview) carry `bodyFormat` and `bodyCss`.
- The browser renders (`frontend/src/features/signage/render/richText.ts`, shared by admin previews and the player): markdown through `marked` (GFM), then markdown and HTML through DOMPurify with scripts, `style` attributes kept, `<style>` elements allowed only in `html`, and `iframe`, `object`, `embed`, `form`, form controls, `link`, `meta`, `base` and event handler attributes removed; URLs only `https:`, `data:image/`, relative and fragments. CSS (the `css` field and `<style>` contents) loses `@import`, `@font-face`, `@namespace`, `expression(`, `behavior:` and `-moz-binding`, and `</style` sequences. The result is placed in a shadow root of the block, so CSS only affects that box; `var(--u)` is available inside. CSP (`script-src 'self'`) remains the second line of defence.
- The backend validates lengths, enums and references only; it never renders HTML. Plain text stays text nodes.
- Server-side announcement placeholders are escaped for the template's `bodyFormat`: HTML-escaped for `html`, markdown punctuation backslash-escaped and HTML-escaped for `markdown`. The shared vectors in `api/testdata/signage-announcement-render.json` cover all three formats.

### Open day, event and agenda lists

- `open_days` and `events` widgets: `count` 1–20 and optional `title` (≤ 200; absent = the previous heading, empty = no heading), `emptyText` (≤ 500), `entryTemplate` (≤ 5 000) plus the rich-text fields. One template is rendered per entry; an empty or absent template keeps the previous row layout. The whole list is one rich-text document, each entry wrapped in `<div class="entry entry--open_day|entry--event">`, so the CSS styles all entries alike.
- New `agenda` widget: open days and events merged by start time: `count` 1–20, `includeOpenDays`, `includeEvents`, `title`, `emptyText`, `openDayTemplate`, `eventTemplate`, rich-text fields, `style`.
- Placeholders `{name}`, values escaped for the format: `{kind}` (`Open day`/`Event`), `{title}` (`Open day` for open days), `{date}` (`Thu 23 Oct`), `{weekday}`, `{weekday_short}`, `{day}`, `{month}`, `{month_short}`, `{year}`, `{start}`, `{end}` (`HH:MM`; empty when unknown), `{status}` (open days: `Scheduled`/`Cancelled`), `{location}` (events; empty when none), `{competencies}` (open days: the planned competencies, comma-separated; empty when none). Unknown placeholders stay as written.
- `open_days` and `agenda` widgets: optional `showCompetencies` (absent = false) adds the planned competencies as outlined chips below the standard open-day row, the first four and `+n`. Templates use `{competencies}` instead. Events widgets reject the field.
- Live data: `openDays` and `events` hold up to 20 entries (`liveListLimit` 20); events gain `endsAt` (nullable). `GET /signage/calendar` follows.

### Calendar widget

- Widget `calendar`: `view` (`month`|`weeks`), `weeks` 1–6 (weeks view, starting with the current ISO week), `showHolidays`, `showBreaks`, `showOpenDays`, `showEvents`, `colors: {holiday, break, openDay, event}` (`#rrggbb`), `showWeekNumbers`, `title` (≤ 200, empty hides), `style`, optional `showCompetencies` (absent = false: in the weeks view open days show their first two planned competencies and `+n`; month cells are too small and cancelled days show none). Weeks start on Monday.
- Live data: `SignagePlayerLive.calendar` (nullable) is present only while the display's publication contains a calendar widget and holds only the categories some published calendar widget shows: `{from, to, holidays: [{date, name}] (≤ 60), breaks: [{name, startsOn, endsOn}] (≤ 20), openDays (≤ 100), events (≤ 100)}`. The range runs from 7 days before the first day of the current month to 49 days after today (makerspace time zone, dates inclusive). Holidays come from the Open Days holiday provider, breaks from `open_day_academic_breaks` (overlapping the range), open days only from published periods and events only from the public calendar, including past entries inside the range. `GET /signage/calendar` returns the same `calendar` block with every category for admin previews.
- The player persists the calendar like open days and events.

## Hiding a run from signage

A person can opt a run out of digital signage (`PUT /machine-runs/{runId}/signage-visibility`, `hiddenFromSignage` on the run, migration `00067`). While a run with the flag is running (a recorded run in state `running`, a manual run before its planned end), its machine is hidden from signage entirely: it is missing from `machines` of `/signage/player/live` and of the admin preview, its camera is not offered to players and a running viewer socket ends within 15 seconds, and automatic camera widgets skip it. The check runs on every live poll (`ListSignageHiddenMachineIDs`), so the machine reappears on its own when the run ends; the flag belongs to the run, so the next run starts visible. A whole job can be kept off signage as well (`hiddenFromSignage` on the job, migration 00097): every run of a hidden job counts as hidden, whatever its own flag says. The machine picker in the admin UI is unchanged.

A camera session is re-checked by Core every 15 seconds, so a viewer socket that was open when the opt-out was set ends with close code 4403 within that time. The player also stops requesting the camera as soon as its next live poll no longer lists the stream.

## Display groups, scene lists, aspect ratios, scene fonts, editor, duplicates and timelapses

Decisions of 2026-11-02 (branch `feat/signage-groups`). The earlier sections of this document describe the resulting state; this section keeps the record and the details. Playlists, orientation and pixel resolutions are gone. Migrations `00090_signage_aspect_ratio.sql`, `00091_signage_scene_lists.sql`, `00092_signage_display_groups.sql`, `00093_signage_scene_font.sql`.

### Aspect ratio instead of orientation and resolution

- `SignageAspectRatio {width, height}`, integers 1–100 each, stored and returned **reduced** (the server divides by the greatest common divisor: `1920:1080` becomes `16:9`). Presets in the UI: 16:9, 9:16, 21:9, 32:9, 4:3, 3:4, plus a custom `W:H`. The schemas `SignageOrientation` and `SignageResolution` are removed; nothing in the API carries pixels any more.
- Displays: `aspectRatio` replaces `orientation` and `resolution` on `SignageDisplay`, `PairSignageDisplayRequest` and `UpdateSignageDisplayRequest`. Columns `aspect_width smallint`, `aspect_height smallint` replace `orientation`, `resolution_width`, `resolution_height` (migration: `resolution_width / gcd(resolution_width, resolution_height)` and the same for the height).
- Scenes: `aspectRatio` replaces `orientation` on `SignageScene`, the create/update requests and `SignagePlayerScene` (migration: `portrait` → 9:16, `landscape` → 16:9). Orientation is derived where rendering needs it: landscape when `width >= height` (`frontend/src/features/signage/helpers.ts`, `orientationOf`), so the design unit `u` (1 % of the design width) and the camera widget keep working.
- Every scene a rule or default list refers to must have exactly the aspect ratio of the display or group it belongs to (422 `validation`, as the orientation check before). A display's aspect ratio cannot change while it is in a group (leave first) and a group's only while it has no members. Changing the ratio of a standalone display while rules or its default list refer to scenes of another ratio is 422 (`… rule(s) show a scene with another aspect ratio; change those rules first`). Changing a scene's aspect ratio while a rule or default list of a display or group with another ratio refers to it is 422 as well.
- Manifest: `display: {aspectRatio, visibleFromOutside}`; scenes carry `aspectRatio`. The player sizes its frame with `aspect-ratio: width / height` (it only ever used the ratio).

### Scene lists replace playlists

- `SignageSceneListItem {sceneId, seconds (3–3600), transition (cut|fade)}`; a scene list is an ordered array of 1–100 items. A one-item list shows that scene continuously (`seconds` is ignored, the UI hides it). A longer list loops with the per-item seconds and transition, exactly like a playlist did.
- Rules: `scenes` (a scene list) replaces `targetKind` and `targetId` on `SignageRule`, `SignageRuleRequest` and `SignagePlayerRule`. `SignageRuleTargetKind` is removed.
- Default: `defaultScenes` (a scene list) replaces `defaultPlaylistId` on `SignageDisplay`, `PairSignageDisplayRequest` and `UpdateSignageDisplayRequest`, and on groups. The manifest carries `defaultScenes` instead of `defaultPlaylistId` and loses `playlists`.
- Tables: `signage_rule_scenes (rule_id FK signage_rules ON DELETE CASCADE, position, scene_id FK signage_scenes ON DELETE RESTRICT, seconds 3–3600, transition, PK (rule_id, position))` and `signage_default_scenes (display_id FK signage_displays ON DELETE CASCADE NULL, group_id FK signage_display_groups ON DELETE CASCADE NULL, position, scene_id FK RESTRICT, seconds, transition, CHECK exactly one owner, UNIQUE (display_id, position), UNIQUE (group_id, position))`. `signage_rules` loses `target_kind`, `target_scene_id`, `target_playlist_id`; `signage_displays` loses `default_playlist_id`; `signage_playlist_items` and `signage_playlists` are dropped.
- Migration data: a rule that showed a scene gets a one-item list (`seconds` 10, `cut`); a rule that showed a playlist gets the playlist's items; a rule whose playlist was empty showed nothing and is deleted (later rules close the position gap). A display's default playlist becomes its default list; a display whose default playlist was empty gets a one-item list with a scene named `Blank` (layout `full`, one `empty` widget, black background, the display's aspect ratio) that the migration creates once per aspect ratio it needs.
- The `/signage/playlists` endpoints, `SignagePlaylist*`, `SignagePlayerPlaylist` and the pending-change kind `playlist` are removed. The remaining kinds are `display`, `rule`, `scene`, `asset`; a changed default list is reported as kind `display` with the name `Default scenes`.
- Deleting a scene is 409 `signage_in_use` while a rule or a default list refers to it (references of kind `rule`, `display` or `group`); scenes only referenced by older publications may be deleted as before.
- Engine (`frontend/src/features/signage/engine/playback.ts`): `PlaybackResult.scenes` (the winning list) replaces `target`; the player (`src/player/view.ts`) and the admin preview rotate the list with the item seconds and transitions; `min_seconds` still applies to the rule, not to an item.

### Stored publications of older shape

Players only play publications, and the stored manifests of a display published before this change still have the old shape. The service upgrades a stored manifest when it reads it (`upgradeManifest` in `backend/internal/signage/manifest.go`, used by the player manifest, the preview and the pending-change diff): new manifests carry `manifestVersion: 3` (now 4, see the conversion above); a manifest without it is converted in memory: `resolution` → `aspectRatio` (reduced), `orientation` dropped, scenes get `aspectRatio` from their orientation, rule targets become `scenes` (a playlist target takes the items of the published playlist; a rule whose playlist was empty is dropped), `defaultPlaylistId` becomes `defaultScenes` (an empty default playlist becomes a one-item list with the first scene of the manifest with the display's ratio, or a synthetic `Blank` scene with a fixed id when there is none), `playlists` is removed. Stored rows are never rewritten; the next publish stores the new shape. The player persists manifests too: it discards a persisted manifest with `manifestVersion` below 4 (or none) and fetches the current one (a network error then shows the waiting screen, not pairing).

### Display groups

A group is a set of displays with one aspect ratio that show the same thing: the group owns the rules and the default list, and publishing the group publishes every member.

- Table `signage_display_groups (id, name 1–100 trimmed, aspect_width, aspect_height, version, created_at, updated_at)`; `signage_displays.group_id uuid NULL REFERENCES signage_display_groups ON DELETE RESTRICT`. `signage_rules.display_id` becomes nullable and `signage_rules.group_id uuid NULL REFERENCES signage_display_groups ON DELETE CASCADE` is added with `CHECK (num_nonnulls(display_id, group_id) = 1)`; `UNIQUE (group_id, position) DEFERRABLE` like the display one.
- A display is either in exactly one group or standalone. In a group it has no rules and no default list of its own: joining deletes them (the UI says so before), leaving gives the display a copy of the group's rules and default list so it keeps showing the same. A display may only join a group with its own aspect ratio (422). `groupId` (nullable) is on `SignageDisplay`, `PairSignageDisplayRequest` and `UpdateSignageDisplayRequest`; with a `groupId` the request's `defaultScenes` must be empty, without one it needs at least one item (422 otherwise).
- Display rule writes (`POST/PUT/DELETE …/rules`, `…/enabled`, `…/rule-order`) answer 409 `display_in_group` while the display is in a group; `GET /signage/displays/{id}/rules` then returns the group's rules (read-only view). `SignageRuleList.displayVersion` is renamed `ownerVersion` (the version of the display or group the rules belong to).
- API (`signage.read` to read; `signage.manage` to create, update, delete and edit rules; `signage.publish` to publish): `GET/POST /signage/groups`, `GET/PUT/DELETE /signage/groups/{groupId}` (`PUT` with `expectedVersion`, `name`, `aspectRatio`, `defaultScenes`; `DELETE` with `expectedVersion`, 409 `signage_in_use` listing the member displays while it has members), `POST /signage/groups/{groupId}/publish`, `GET /signage/groups/{groupId}/preview`, and the rule endpoints mirrored under `/signage/groups/{groupId}/rules`, `…/rules/{ruleId}`, `…/rules/{ruleId}/enabled`, `…/rule-order` with the same request and response shapes as the display ones (the group's `expectedVersion`). Handlers share the service code through an owner (`display` or `group` id).
- `SignageDisplayGroup {id, name, aspectRatio, defaultScenes, displayIds (members by display name), pendingChanges, version, createdAt, updatedAt}`. `pendingChanges` is the union (deduplicated) of the diff between the group's draft manifest and each member's latest publication; a member that was never published contributes nothing (its own `publishedRevision` is null). `GET /signage/groups` returns `{items}`.
- Publishing a group stores one publication per member in one transaction (same content, each with its own `visibleFromOutside`) and audits `signage_display_group.published` with the display ids; publishing a single member through `POST /signage/displays/{id}/publish` keeps working and uses the group's content. A member's `pendingChanges` compare the group's draft manifest for that display with its latest publication.
- The group preview returns the latest publication of the first member (by name) that has one with that member's live data, `manifest` null when none has one.
- Audit: `signage_display_group.created|updated|deleted|published`; rules of a group are audited like display rules with `groupId` in place of `displayId`.
- Announcements: `groupIds` (≤ 50) is added next to `displayIds` on `SignageAnnouncement`, `StartSignageAnnouncementRequest` and `UpdateSignageAnnouncementRequest`; with `allDisplays` both must be empty, without it at least one of them must be non-empty. Table `signage_announcement_groups (announcement_id FK CASCADE, group_id FK CASCADE)`. An announcement is in force for a display when it targets all displays, the display, or the display's current group (evaluated live, so a display that joins a group picks the group's announcements up on its next poll).
- Membership and audit details: leaving a group with an empty `defaultScenes` keeps a copy of the group's default list (the member's own list is empty, so its settings form sends `[]`); a non-empty list replaces it. Switching directly from one group to another is a join (no copy). Publishing a group without members that can play (none, or all revoked) is 422. The audit log has no list-valued metadata, so a group publish writes `signage_display_group.published` (changed fields `revision`, `displayIds`) plus one `signage_display.published` per member (changed fields `revision`, `groupId`); group rule audits name `groupId` in their changed fields and group reorders are `signage_display_group.rules_reordered`. Rolling back `00092` copies each group's rules and default list to its members and turns group targets of announcements into display targets; groups without members and the groups themselves are lost.
- Admin UI: the Displays page gets a **Groups** section (table: name, ratio, members, pending changes) with a "New group" modal; a group page `/signage/groups/{id}` with the tabs Playback (rules and default list, same components as the display page), Members (add or remove displays; only displays with the ratio are offered) and Settings (name, aspect ratio) plus the Publish button with the pending-change list. The display page shows "Managed by group …" with a link and the group's rules read-only in its Playback tab while the display is in a group; the display settings and the pairing modal get a group picker (filtered by ratio). The announcement start and edit dialogs offer groups next to displays.

### Scene font

- `signage_scenes.font_family text NOT NULL DEFAULT 'sans' CHECK (font_family IN ('sans', 'serif', 'mono', 'custom'))` and `font_asset_id uuid NULL REFERENCES signage_assets ON DELETE RESTRICT` with `CHECK ((font_family = 'custom') = (font_asset_id IS NOT NULL))` (migration `00093`).
- API: `fontFamily` (`SignageSceneFontFamily`: `sans|serif|mono|custom`) and `fontAssetId` (nullable) on `SignageScene`, `SignagePlayerScene` and the create (optional, default `sans`) and update requests. The scene font reaches the manifest's assets like widget fonts; deleting a font a scene uses is 409 `signage_in_use` with a `scene` reference.
- Rendering: the scene root gets the font stack (or the uploaded font's `@font-face` family); a widget style with `fontFamily` `inherit` ("As the scene") inherits it. The scene editor gets the font fields in its scene settings next to the theme.
- Font bug (fonts chosen in a widget stayed selected but the preview and the display fell back to the default font): registration moved to the CSS Font Loading API with retries (`registerFontFaces` in `render/style.ts`; backoff 5 s, 30 s, 2 min, 10 min, then every 30 min, and at once on the next call for a face in `error` status), because a failed load (network blip, restart, token rotation, cache miss) was never retried for the lifetime of the document; the exact trigger was not reproduced. The `<style>` path remains as the fallback without the API.

### Clock widget: date mode

`SignageClockWidget.mode` gains `date`: the big line shows the weekday, day, month and year (`Monday 2 November 2026`, en-GB, makerspace time zone), no time. `time` and `datetime` are unchanged.

### Duplicating scenes and announcement templates

`POST /signage/scenes/{sceneId}/duplicate`, `POST /signage/announcement-templates/{templateId}/duplicate` (`signage.content.manage`) answer 201 with the copy: every field of the source, a fresh id and version 1, named `<name> (copy)`, `<name> (copy 2)`, … (the first name not taken, truncated to fit 100 characters). Template copies take the fields along; scene copies take the blocks. Audited as `*.created`. The UI offers "Duplicate" in the row menus of the Content page and opens the copy.

### Scene editor: autosave, undo and redo

The screen editor (`/signage/scenes/{id}`) has no Save or Discard. Edits change an in-memory draft that `useAutosave` sends with `PUT /signage/scenes/{id}` 800 ms after the last change, one request at a time, quoting the version of the last response as `expectedVersion`; the header shows the state (saved, saving, error with retry). A draft that would certainly be rejected (empty name, invalid colour) is shown as a problem and not sent. A 409 `stale_write` stops saving and offers "Load latest" (drops local changes) or "Keep mine" (saves over it). Leaving the page with unsaved changes saves first (`useUnsavedChanges`). **Undo** / **Redo** (Ctrl/Cmd+Z, Ctrl/Cmd+Shift+Z or Ctrl/Cmd+Y; header buttons) walk an in-memory history of up to 100 draft states (`editorHistory.ts`; consecutive edits of the same field within 500 ms are one step). Publishing and preview are in the header (`signage.publish` for Publish).

### Timelapse widget

Shows the timelapse videos of recent prints as a slideshow.

- Widget `timelapse`: `source` (`all`|`machines`), `machineIds` (≤ 20, distinct existing machines; required non-empty with `machines`, must be empty with `all`), `count` 1–20 (newest clips), `maxAgeDays` 0–365 (0 = any age; otherwise only runs that ended within that many days), `maxSeconds` 5–600 (a clip plays fully but at most this long), `transition` (`cut`|`fade`), `showCaption` (machine name and the day the print ended, bottom left; never the job, file or person), `fit` (`cover`|`contain`), `style`.
- Which runs: recorded runs in state `finished` with a stored timelapse (`machine_run_timelapses`) whose `hidden_from_signage` is false and whose job is not hidden from signage (a hidden run never shows its timelapse, not only while it runs), of the widget's machines, ended within `maxAgeDays`, newest first, `count` of them. Machines currently hidden by a running hidden run still show their earlier clips.
- Live: `SignagePlayerLive.timelapses` (nullable, present only while the display's publication contains a timelapse widget) lists the union of what the published timelapse widgets need, newest first, at most 50: `{runId, machineId, machineName, endedAt, sha256, sizeBytes, url}` with `url` the relative path `/api/v1/signage/player/timelapses/{runId}/{sha256}`. The admin preview returns the same block; the admin UI loads the video through `GET /signage/timelapses/{runId}/content?v=<sha256>` (`signage.read`; 404 unless the run is finished, not hidden from signage and has that timelapse; `Cache-Control` as for assets).
- Player endpoint `GET /signage/player/timelapses/{runId}/{sha256}`: the video bytes with HTTP Range support and `Cache-Control: private, max-age=31536000, immutable`, only while the run is in the display's current timelapse selection (recomputed from the publication on each request) and the digest matches; 404 otherwise. Rate-limited like asset downloads (600/minute per device).
- Player caching: the runtime keeps the listed clips in the Cache Storage cache `signage-timelapses-v1`, keyed by their player URL path (which embeds the sha256), downloading newly listed clips one at a time after the manifest's assets, evicting clips no longer listed, and skipping a clip that does not fit the free quota (reported in the heartbeat errors). The service worker answers the player timelapse path from that cache including byte ranges, like assets. The list is persisted with the other live data (24 h). A clip that is not cached yet is skipped by the widget until it is; without Cache Storage the widget plays the clips from the network.
- Rendering (shared renderer, the widget code is a lazily loaded chunk like the calendar widget, so the player bundle budget holds): clips newest first, each from the start until it ends or `maxSeconds` pass, then the next with the transition; a widget without clips shows only its style box. Admin previews play the clips the same way.
