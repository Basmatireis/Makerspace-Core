# Terminal, attendance, session policies, and surveys

The entrance terminal is an ordinary registered ManagedDevice with `terminal_enabled`, an explicit SessionPolicy, attendance assurance settings, checkout mode, and declared hardware capabilities. The public `/terminal` route accepts only a valid managed-device credential. It never consumes an existing staff Session, so public requests cannot inherit staff permissions. Staff sign-in creates a Session bound to that device. Server authentication rejects that Session without the same active device identity, and idle or absolute expiry makes it unusable before the browser redirects to the policy destination.

Unregistered browsers use the one default SessionPolicy and are never inserted into `managed_devices`. Sessions snapshot the selected policy ID/version, idle interval, absolute deadline, post-session destination, and optional device ID. User activity extends idle expiry through `POST /auth/activity`, capped by the absolute deadline. Policy or device-policy changes revoke affected active Sessions transactionally.

Attendance is separate from authentication. Password or PIN verification at the terminal returns a verified Person/Account/assurance result without creating a Session. Check-in locks the enabled Account and Person, prevents two open Visits, evaluates the existing Lab Rules state, and creates the existing confirmation request when action is needed. A role in `warning` mode is admitted with a warning. A role in `blocking` mode gets a held check-in instead of a Visit (`202` with an `AttendanceHold`): at most one per Person, it lapses at the next local midnight (`MAKERSPACE_TIME_ZONE`), and a repeated attempt the same day keeps it. Confirming the person's Lab Rules request completes the hold in the same transaction, so the Visit starts at confirmation; a confirmation after the hold lapsed admits nobody. Staff list holds with `attendance.read` (`GET /attendance/holds`) and cancel them with `attendance.assist`; the cleanup command deletes lapsed holds. Supervised operations use registered attendance permissions; voiding requires `attendance.correct`, an optimistic version, and a reason. Each mutation and its audit event share a transaction.

Completing visitor enrollment on the terminal counts as arriving, in the enrollment transaction (check-in method `enrollment`, assurance `low`, checked in by the new account, on the enrollment device). A role in `blocking` mode gets a hold, so the new person appears as "Awaiting sign-off" and is checked in automatically when a supervisor confirms their Lab Rules; any other role gets a Visit right away (admission `warning` when Lab Rules confirmation is still open, else `admitted`). The enrollment result reports this as `attendance` (`checked_in` or `awaiting_sign_off`); the visitor does not check in again.

Public presence exposes only first name plus surname initial and Visit ID; held check-ins appear the same way under `waiting`. The terminal lists them first in the single "Currently here" list with an "Awaiting sign-off" tag (not tappable for checkout, since they have no Visit) and refetches presence every 10 seconds. The staff attendance page shows held people as "Awaiting sign-off" rows in its "Currently here" table (confirm Lab Rules, cancel check-in), shows a prominent notice at the top whenever Lab Rules confirmations are pending: people at the entrance first (confirm with `laborordnung.confirm`, cancel with `attendance.assist`), then other open confirmation requests for `laborordnung.requests.read`, and no notice when nothing is pending, and refetches visits, holds and the queue every 5 seconds while the tab is visible. Public-tap checkout is available only when the device policy enables it. Detailed completed/voided Visit rows are retained for 90 days by the cleanup command. Before completed Visit detail is deleted, non-identifying daily counts, durations, daily unique counts, and peak occupancy are accumulated in `attendance_daily_statistics`. Exact interactive statistics are limited to a 90-day range.

Surveys have editable drafts, immutable published versions, ordered typed questions, options, and optional `visit_checked_out` triggers. Supported question kinds are single choice, multiple choice, free text, rating, and yes/no. Closing a Survey disables its trigger and cancels outstanding invitations. Checkout creates eligible invitations in the Visit transaction. The `deliver-surveys` admin command claims due deliveries safely and sends through the generic Notifications service; email is implemented and the SMS provider remains an interface.

Invitation tokens are HMAC-derived opaque values whose digests alone are stored. Delivery identity and response data use separate tables. Redeeming an anonymous invitation stores no `identified_person_id`, clears Person, Visit, and recipient fields from the invitation in the same transaction, and a database trigger rejects identified responses for anonymous Survey versions. Submitted dates and operational delivery timestamps still create limited timing-correlation risk, which administrators should consider when cohorts are very small.

The web bridge contract is versioned and selected at runtime. Android injects `window.makerspaceDeviceBridgeNative`; the Tauri shell injects a private loopback bridge configuration. Both report capabilities and emit only technical credential events (`nfc`, `qr`, or `barcode`). The web application and Core own resolution and business rules. The current desktop implementation supports PC/SC NFC UID reads; concrete USB drivers and other hardware adapters remain separate deployment work.
