# PDF templates

The PDFs of the system are rendered from editable templates: the **wiRef invoice request** (mail attachment and settings preview), the **cashbook** (the HTU Kassabuch sheet of the cashbook export), the **receipt** of an order and the **Projektantrag** of a working-group project (with its Vorschussantrag, cost plan and planned purchases). Without a published template each export uses a built-in default that reproduces the PDFs of release 0.19 (the receipt is new; the Projektantrag default reproduces the form the working groups drew before, see below). The editor is under Settings › PDF templates; the contract is the tag "PDF Templates" in `api/openapi.yaml`.

## Concepts

- **Document.** A template is a JSON document (`schemaVersion` 1): page set-up, document styles (colours, text styles, sizes), fixed-position layers and the header, body and footer block lists. It is decoded strictly (unknown properties, wrong types and out-of-range values are `422 pdf_template_invalid` with the violations); the model, expression language and renderer are the pure package `backend/internal/pdftemplates/engine`.
- **Versions.** Per export there is at most one **draft** and one **published** version; older published versions are **archived**. Saving replaces the draft (`PUT .../draft`, `expectedRevision` guards against concurrent saves, `409 stale_write`), publishing turns the draft into the published version and archives the previous one, restoring copies any version into the draft, discarding deletes the draft. No stored version means the built-in default is in effect ("reset to default" is discarding the draft and publishing the built-in document).
- **Problems.** `engine.Check` reports `error` and `warning` problems per node (unknown variable or filter, dangling style reference …). A draft may be saved with problems; publishing is refused with `422 pdf_template_has_problems` while an error exists.
- **Effective template.** `pdftemplates.Service.Effective` returns the published document, else the built-in one (the wiRef default takes the branding primary colour as its `accent` colour). `RenderEffective` renders data with it; the real exports call it: `invoicing` for the mail attachment and the settings preview, `orders.ExportCashbook` for the PDF, `orders.ReceiptPDF` and `workinggroups` for the Projektantrag (preview, wiRef mail and the request PDF stored at send time). A stored document the engine can no longer read falls back to the built-in default (logged without content).
- **Images.** PNG, JPEG and SVG (paths only) up to 2 MiB, at most 100 images, stored in the database. The type is sniffed from the content. An image used by the draft or the published version cannot be deleted (`409 pdf_template_asset_in_use`).

## Blocks for forms

- **Grid** (`type: "grid"`): a static form table for the body or a layer. `colWidths` are the column widths in millimetres (1–20), `rows` (1–100) each have a minimum `height` and `cells`; a cell has `text` (expressions allowed), `align` (left, center, right), `valign` (top, middle, bottom), `textStyle`, `size`, `weight`, `color`, `fill` and `span` (columns it covers; the spans of a row may not exceed the columns, missing cells are empty framed cells). `stroke` (default 0.17 mm, 0 draws no frame), `color` and `padding` (horizontal text inset, default 1.88 mm) apply to the whole grid. A row grows when its text needs more room. Text is placed by the height of capitals: `middle` centres from the top of the capitals to the last baseline, `top` and `bottom` keep half the padding free. A grid is unbreakable, takes its width from its columns (its `w` is ignored) and abuts the next block, so stacked grids read as one form. The built-in Kassabuch uses grids for its head block and its closing sheet.
- **Image from the data** (`image` with `source`): an image block without `source` places the branding logo; with `source` naming an image variable of the export (the Projektantrag's `signature`) it places that image at the block's height, never wider than the column, and draws nothing without one. The checker refuses a source that is not an image variable. In text an image variable is empty.
- **Built-in artwork** (`graphic` with `art`): the HTU letterhead in its parts `htu-logo`, `htu-corner-top`, `htu-corner-bottom` and `htu-footer`, each drawn into its box from its own outline (`engine.Arts()` lists their natural size and position on A4), and `htu-letterhead`, the whole letterhead on an A4 page, kept for stored templates.

## Preview layout map

The preview returns, besides the PDF, a box per node and page (`boxes`, pages counted from 1), the problems, the redacted fields and `inactive`: the ids of the nodes that drew nothing with this data — a branch of a condition or switch that was not taken, a loop without entries, a layer whose pages the document does not have, a text that came out empty. The editor marks them as not shown with this data. Layers have no box of their own (it would cover their elements), a line's box is at least as thick as its stroke, and a logo block keeps a square of its height when the branding has no PNG or JPEG logo.

## Permissions and audit

Every operation needs `pdf_templates.manage`. It is a **high-trust permission**: a published template changes the Kassabuch that is printed and signed for the HTU, the PDF that is mailed to wiRef as the basis of an invoice and the signed Projektantrag mailed to the wiRef, so only people who may be trusted with that wording and those figures should hold it. The role holder is a deliberate choice, no role has it by default (master holds every permission). A preview with a real record additionally needs the permission of the export: wiRef `external_invoice_requests.read` and `orders.read` (the document lists the order's payments, which the request API shows only with `orders.read`), cashbook `payments.read` and `cash_movements.read`, receipt `orders.read`. The renderer receives the caller's permissions: a variable that needs a permission the reader lacks (`lines[].customer`, `lines[].orderSummary`: `orders.read`; `order.customer.matriculationNumber`: `people.read.matriculation`) renders empty and is listed in `redacted`. Sample previews show every field. The wiRef mail is a system rendering: its schema has no sensitive fields. The receipt PDF endpoint needs `orders.read` and leaves the matriculation number out without its permission.

Audit events (same transaction as the change): `pdf_template.draft_saved`, `.draft_discarded`, `.published`, `.restored`, `pdf_template_asset.uploaded`, `.deleted`. Details are the export kind, the version number and an asset id, never document content.

## Security model

Template text is data: values are inserted as plain text and never interpreted again; the expression language is closed (no arithmetic, no calls except the filters). Size limits: document 256 KiB, 500 nodes, nesting 16, text 4000 characters per field, 300 pages, 10 s render deadline, 20 MiB output (`pdf_template_too_large`, `pdf_render_limit`). Uploaded PNG and JPEG images are decoded and encoded again before they are stored (so EXIF and GPS data, text chunks and trailing bytes never reach the database or a PDF; a JPEG loses its orientation tag), and uploaded SVGs are reduced to their path outlines; image ids in a document must be canonical lower-case hyphenated UUIDs, and publishing is refused (`pdf_template_has_problems`) when an image the document places no longer exists; asset downloads carry `Content-Security-Policy: default-src 'none'; sandbox` and `nosniff`. Template text, data values and rendered output are never logged.

## Data per export

The authoritative list, with descriptions and examples, is `engine.Schema(kind)` (returned by `GET /pdf-templates/{export}` as `schema`); tests assert that the data built by the owning packages matches it exactly (`pdftest.AssertData`). Always available: `makerspace.name|displayName|address|logo`, `generatedAt`, `page`, `pages` and the form-table locals `sheet.*`.

- **wiref** (built by `invoicing.Document.PDFData`): `request.*` (number, orderNumber, approvedAt, approver, servicePeriod.from/to, serviceDescription), `recipient.*`, `amounts.total|alreadyPaid|toInvoice`, `texts.title|intro|closing` (the PDF texts of the wiRef settings with their `{{placeholders}}` already filled in), `show.*` ("true" or empty for the optional parts the settings switch on; the values of a part that is switched off, such as `recipient.contactName`, `recipient.contactChannel`, `request.approver`, `recipient.purchaseOrderReference`, the service period and the service description, are empty in the data, so a custom template cannot print them), lists `items[]` and `payments[]`. The settings page keeps these texts; its PDF section links to the editor.
- **cashbook** (built by `orders.cashbook.pdfData`): `period.*` (`from`, `to`, `businessYear`, `contents`, and `kind`: `cash-register` or `all-payments`, which the default file name uses), `organization.*`, `totals.*` (opening and closing empty for an export of all payments), list `lines[]` with `text` (the German description as on the paper form), `orderSummary` and `customer` (only with `orders.read`), `in`, `out`, `balance`. The default file name is `cashbook-<from>-<to>.pdf`.
- **receipt** (built by `orders.receiptData`): `order.*` (number, createdAt, customer.name, customer.matriculationNumber, total, paid, open), `payment.*` (only for the receipt of one payment), lists `items[]` and `payments[]`.
- **projektantrag** (built by `workinggroups.projektantragData`): `form.*` (the stored or edited request: unitKind as "Stv", "UV" or "Referat/Studi-Lab", unitName, number, projectName, alcohol and advance as "Ja"/"Nein", startsOn, endsOn, people, description, maxExpenses, maxIncome, responsibleFirstName, responsibleLastName, responsibleName, place, date), `signature` (image), `project.*` (title, group, goal, benefit, paidFrom as "Gruppenbudget"/"Externe Quelle", wirefNumber, plannedTotal, plannedIncome), `advance.amount` (the advance amount, else the planned total), list `items[]` (position, text, link, note, plannedAmount, needsOffers, chosenOffer) with the nested list `items[].offers[]` (shop, price, chosen, attached; loop over `item.offers` inside an item loop), and list `purchases[]` (the item purchases that are not declined: item, costItem, quantity, unitPrice, total, link, status in German, attached). The schema has no permission-gated fields; the rendering is a system rendering. It has no real records to preview, only the sample. The built-in default prints the form, the Vorschussantrag when `form.advance` is "Ja", the cost plan with the comparison offers of the items that need them, and the planned purchases, each part on a new page, in Helvetica with German labels; its file name is `Projektantrag.pdf`.

Previews of real records offer the last 10 approved wiRef requests, the last 3 calendar months of the cash register and the last 10 finalized orders with a receipt. A source is labelled by its reference only (request number, month, order number), never by a customer or recipient name.

## Versions and drafts

A discarded draft is deleted, so the next draft of that export reuses its version number; the audit events carry the resource id as well. Restoring a version replaces the current draft and discarding deletes it, both without a revision check: the editor asks for confirmation first. Listings are bounded (500 versions per export, `MaxAssets` + 1 images).

## Retention

Archived versions and unused images stay until an administrator deletes them (privacy category `configuration.pdf_templates`); the accounts that created or published them are listed under `platform.actor_references`.

## Receipt PDF

`GET /orders/{orderId}/receipt.pdf?paymentId=` (`orders.read`) renders the effective receipt template for a finalized order with a settled amount (`409 receipt_not_available` otherwise); `paymentId` must be a payment that still counts towards the order (404 otherwise). The receipt page offers it as "Download PDF" next to Print.
