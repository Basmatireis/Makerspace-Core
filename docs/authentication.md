# Authentication and sessions

## Identities and assurance

An Account can have password, PIN, and OIDC identities. Every Account has a password login email (the password identity; a password may still be unset), and that address is also the Person's only email: `people.email` mirrors it and is changed in the same transaction by the login-email operation (`accounts.login_email.update`), Account creation (which requires `loginEmail`), SCIM (primary email), OIDC just-in-time provisioning (verified email claim, skipped when another Account already uses it) and visitor enrollment. `PATCH /people/{id}` rejects a different email for a Person with an Account (422 `email_managed_by_account`). Accounts provisioned without an email (phone-only visitors, accounts created before this rule) show `loginEmail: null` and a warning on the person page until an administrator sets one. A changed normalized login email loses its previous verification and outstanding password challenges. Failed password login returns the same `invalid_credentials` behavior for unknown email, wrong password, disabled account, unset password, and reset-required credential.

New passwords contain 12–128 Unicode characters, at most 1,024 encoded bytes, and cannot appear in the [attributed bundled common-password list](../backend/internal/security/COMMON_PASSWORDS_LICENSE.md). Existing-password inputs remain opaque so policy changes do not lock out older valid credentials. Argon2id uses a random 16-byte salt, 64 MiB memory, three iterations, one lane, and a 32-byte result. Successful login upgrades valid older hash parameters. The process-local password limiter allows ten attempts per hashed source/email key in fifteen minutes and has a 4,096-key bound.

Administrators with `accounts.password.set` may set an Account's password directly (`PUT /accounts/{id}/password`); this needs no mail configuration, revokes the Account's sessions and outstanding reset challenges, and writes its audit event in the same transaction. A password requires the login email (password identity): for an Account without one the operation answers 422 and the person page first sets the email (`accounts.login_email.update`) in the same dialog. Only a master may set the password or login email of a master Account. PIN login uses a case-insensitive username and a 6–12 digit PIN. PIN hashes use Argon2id plus a deployment pepper; database throttles track keyed username and source digests with increasing delays. PIN sessions have `low` assurance, password sessions `normal`, and password-plus-second-factor and passkey sessions `strong_mfa`. Self PIN enrollment/removal requires the dedicated permission and authentication within ten minutes at least at `normal` assurance. Authorized administrators may configure a username and PIN directly without an email address, or issue a recipient-owned setup challenge. Either path stores only the PIN hash, revokes affected sessions, and writes its audit event transactionally. Account activation and authentication methods are independent: an active Account may have no usable method and therefore cannot sign in until one is configured. Usability means an enabled password identity with a non-reset credential, an enabled PIN identity with a credential, or an enabled OIDC identity whose provider is enabled.

The administrative Person view can remove password, PIN, and individual OIDC methods when the actor has the corresponding `*.remove.all` or `identities.oidc.unlink.all` permission. Removal is version-checked, deletes dependent credentials and challenges, revokes Account sessions, and writes the method-specific audit event in the same transaction. It never activates or deactivates the Account.

OIDC uses authorization code flow, S256 PKCE, nonce, and a ten-minute single-use database flow bound to a separate browser cookie. State and browser tokens are digested; nonce, PKCE verifier, and client secrets are encrypted. The OIDC library validates signature, issuer, audience, and expiry; the service verifies nonce. Identity is the exact issuer/subject pair, never an email/name match. Optional JIT creates a new Person with no Roles and an enabled Account, requiring contact information. Only exact configured ACR values raise assurance to `strong` or `strong_mfa`; unknown values remain `normal`. Self-linking requires `identities.oidc.link.self` and at least `normal` assurance from authentication within five minutes. Supplying the optional current password refreshes that proof with bounded password attempts. OIDC-only Accounts use an already linked enabled provider via `POST /auth/oidc/{providerSlug}/reauthenticate`. This requests `max_age=0` and `prompt=login`, verifies signed `auth_time` against the start of the flow, and requires the exact linked issuer/subject to belong to the same Account. It updates the existing session assurance fields for five minutes; it cannot JIT-provision or link during reauthentication. These checks follow [OIDC Core authentication-age semantics](https://openid.net/specs/openid-connect-core-1_0.html#AuthRequest). A normal OIDC login without `auth_time` provides login access but no recent-authentication proof. PIN alone remains `low`, including on a managed device, and cannot authorize linking. Linking callbacks recheck the active session, current permission, Account state, and proof expiry.

Disabling an OIDC provider prevents new logins, linking, and reauthentication, including completion of in-flight flows. It leaves existing application sessions valid until ordinary expiry/revocation or Account/identity invalidation. Disabled providers and disabled identities are not usable authentication methods. No automatic mass session revocation is performed. Unlinking checks self/all permission but may leave an active Account without a login method.

`identities.oidc.link.all` is retained for contract compatibility but reserved and unimplemented. There is no administrative endpoint to assign a subject or attach an external principal to another Account.

Assurance and managed-device scope are independent grant requirements. A kiosk does not raise the user's authentication assurance. See [authorization](authorization.md) and [managed devices](managed-devices.md).

## Second factors

An account may enrol an authenticator app (TOTP) and any number of passkeys. Enrolment and self-management need only a staff session, no permission, because accounts that must use a second factor have to be able to set one up whatever their roles grant. Starting or confirming an enrolment needs `normal` or higher authentication within the last ten minutes; removing a factor or regenerating recovery codes needs `strong_mfa` within the last ten minutes (`403 reauthentication_required` otherwise).

- **TOTP** follows RFC 6238 with SHA-1, six digits, 30-second steps and one step of drift. The 160-bit secret is encrypted with the application keyring (`APP_ENCRYPTION_KEYS`) and shown once, with its `otpauth://` URI (issuer: the host of `PUBLIC_BASE_URL`). An unconfirmed enrolment can be confirmed within ten minutes; an account has at most one confirmed app. The last accepted time step is stored, so a code is never accepted twice.
- **Recovery codes**: the first second factor of an account generates ten single-use codes (`XXXXX-XXXXX`, unambiguous alphabet), returned once; only keyed HMAC digests are stored. They can be regenerated, and removing the last factor deletes them.
- **Passkeys** use `go-webauthn/webauthn`. The relying party ID is the host of `PUBLIC_BASE_URL` and its origin the only accepted origin. Registration requires a discoverable (resident) credential and user verification and excludes already registered credentials; the user handle is the account ID. Every ceremony's state is stored server-side (`webauthn_challenges`), bound to its purpose and to the session or pending login that requested it, looked up by the digest of the signed challenge, deleted before verification (single use) and valid for five minutes. A signature counter that does not increase rejects the assertion (`passkey_clone_suspected`). A passkey assertion with user verification counts as `strong_mfa`.

Wrong second factors are throttled per account in PostgreSQL with the PIN back-off (one second, doubling to five minutes, reset after a quiet quarter hour; `429 second_factor_rate_limited`) and audited as `auth.second_factor_failed` with the method only. Enrolment, removal, regeneration and reset write `account.totp_enrolled`, `account.passkey_registered`, `account.passkey_renamed`, `account.totp_removed`, `account.passkey_removed`, `account.recovery_codes_regenerated` and `account.second_factors_reset` in the same transaction. Removal revokes the account's other sessions; deleting a passkey also ends the sessions signed in with it.

### Login with a second factor

A correct password of an account with an authenticator app or a passkey creates no session: `POST /auth/login` answers `202` with the available methods and sets an HttpOnly pending-login cookie. The pending login stores only the token digest, the account, identity and managed device, expires after five minutes, is single-use, and ends after five wrong second factors. It is completed with a TOTP or recovery code (`POST /auth/login/second-factor`) or a passkey assertion (`/auth/login/second-factor/passkey/options` then `/auth/login/second-factor/passkey`); completion locks the Account, rechecks the password identity, and creates a `strong_mfa` session. `POST /auth/passkey/options` and `/auth/passkey/login` sign in without a username using a discoverable passkey (`strong_mfa`, `auth_method = passkey`). PIN login stays `low` and has no second-factor step. An OIDC login gets the assurance its configured ACR maps to; a local second factor is not asked for there, but the session can be raised by reauthentication.

Accounts without a second factor sign in with `normal` as before. An account **must** use a second factor when it holds the master role or a role with a grant that requires `strong_mfa`. Such an account without one may still sign in with a password (or OIDC below `strong_mfa`), but the session is flagged `mfaSetupRequired`: every operation except `GET /auth/me`, logout, session activity, reauthentication and second-factor enrolment (operations marked `x-mfa-setup-allowed` in the contract) answers `403 mfa_setup_required`. Enrolling the first factor raises the session to `strong_mfa` and lifts the flag (also for other flagged sessions of the account). The flag is also derived on every request: a session below `strong_mfa` of an account that must use a second factor and has none is confined the same way, which covers sessions created before second factors existed and accounts that gain the master role or a `strong_mfa` grant later. An account that has a second factor but a session below `strong_mfa` (for example after an OIDC login without a multi-factor assertion) sees a notice in the application with a "Confirm with second factor" action, which runs reauthentication and unlocks the permissions that need it. Administrators with `accounts.mfa.reset` remove all second factors of another account (only a master for a master account), which revokes its sessions.

### Fresh sign-in and reauthentication

Each session records `authenticated_at` and the assurance proven then (`authenticated_assurance`). `POST /auth/reauthenticate` verifies the password (Argon2id before any transaction, compared again under the Account lock) and, for an account with a second factor, a TOTP or recovery code; that proof is `strong_mfa` and raises the session to `strong_mfa`. Without a second factor the proof is `normal`. `POST /auth/reauthenticate/passkey/options` and `/auth/reauthenticate/passkey` reauthenticate with a passkey (`strong_mfa`). A weaker proof never lowers a session; a proof above the session's base assurance that is not multi-factor lasts five minutes, as before. Grants and the master policy that require a fresh sign-in compare against the proven assurance and time (see [authorization](authorization.md)). `GET /auth/me` returns `authentication` with the method, assurance, `authenticatedAt`, `authenticatedAssurance`, `mfaEnrolled`, `mfaRequired`, `mfaSetupRequired`, the available second-factor methods and the permissions withheld until a fresh sign-in.

### Second factors in the web interface

All second-factor screens live in lazily loaded chunks (`frontend/src/features/auth/mfa/`); the login page and the application shell only carry small triggers, so the initial bundle budget is unaffected. The permission ids used by the entry code are string literals typed by the generated `PermissionId` type, so the generated object does not enter the initial graph.

- **Login.** After a `202` the login page shows the second-factor step: authenticator code (numeric, `autocomplete="one-time-code"`), a toggle to a recovery code, and "Use a passkey" when the account has one and the browser has `PublicKeyCredential`. Wrong or throttled codes show an inline error; an expired pending login (`second_factor_pending_invalid`) offers to start again. "Sign in with passkey" (usernameless, `/auth/passkey/*`) is hidden without WebAuthn support. Binary WebAuthn members are converted with small base64url helpers (`webauthn.ts`); the serialized credential is `PublicKeyCredential.toJSON()` where available.
- **Forced setup.** While `authentication.mfaSetupRequired` is set, `ProtectedRoute` renders a full-page "Set up a second factor" screen instead of the application (authenticator app and passkey registration). The authenticator panel shows a QR code of the `otpauth://` URI, rendered client-side as an SVG from the `qrcode` package in a lazily loaded chunk outside the initial bundle, with the key as a copyable fallback and an open-in-app link for the same device. Recovery codes are shown once (copy or download as `.txt`) before `/auth/me` is reloaded. Any `403 mfa_setup_required` reloads the current user, which leads to the same screen.
- **Profile.** "Two-factor authentication" (the same enrolment panel) lists the authenticator app, passkeys (name, created, last used; rename, remove) and the remaining recovery codes (regenerate).
- **Step-up.** `apiFetch` answers `403 reauthentication_required` by opening a "Confirm it's you" dialog (password plus authenticator or recovery code, or a passkey) and repeating the original request exactly once after success; cancelling rejects with the original error. Concurrent failures share one dialog, and the `/auth/reauthenticate*` endpoints never prompt. The dialog is loaded on demand in its own React root, so every screen benefits without wiring.
- **Withheld permissions stay visible.** The frontend's `hasPermission` counts a permission that `/auth/me` lists under `authentication.reauthenticationRequired` as held, so navigation entries, settings screens and controls that need it do not disappear once a master's fresh-sign-in window has passed; the first request that needs the permission opens the dialog above and is repeated. `isPendingPermission` tells the two apart where a screen wants to say so. Data the API withholds is not shown, because the UI only ever renders what the API returned.
- **Roles and people.** The role editor sets "Require fresh sign-in within N minutes" (1–1440) per access rule, and masters edit the master reauthentication policy from the roles toolbar. A person's detail page lists the account's second factors (`accounts.read`) and offers "Reset second factors" with `accounts.mfa.reset`. These checks only shape the interface; the API enforces them.

## Server-side sessions and browser protection

Successful password, PIN, and OIDC login generates random session and CSRF tokens. PostgreSQL holds SHA-256 digests, never usable tokens. Sessions record Account/identity, authentication method, base/current assurance, authentication/last-seen times, idle/absolute expiry, and revocation. Defaults are a sliding six-hour idle lifetime and fixed 72-hour absolute lifetime. Current Account status, identity disablement, password reset state, and permissions are evaluated on requests rather than cached in a JWT.

Password/PIN login and security-sensitive Account mutations lock the Account. Password challenge completion also locks the Account before the challenge and revalidates its identity after waiting. OIDC session creation rechecks Account status and identity ownership/disablement under that same lock. Administrative password changes, login-email changes, and recovery invalidate password reset/invitation/verification challenges and revoke sessions. An already-issued self-service recovery challenge intentionally remains redeemable after a self password change, matching the existing concurrency test.

Development cookies are `makerspace_session` (HttpOnly) and `makerspace_csrf` (readable by the frontend), both SameSite=Lax and Path=/. Production requires HTTPS and secure cookies with corresponding `__Host-` names, Path=/ and no Domain. OIDC flows and visitor contexts use separate cookies. A managed-device header or HttpOnly device cookie identifies a kiosk, not a user; invalid/expired/revoked device credentials are treated as absent.

Unsafe browser requests require an Origin matching `PUBLIC_BASE_URL`. Unsafe session-authenticated requests additionally mirror the CSRF cookie in `X-CSRF-Token`; the server compares cookie/header in constant time and checks the stored digest. Visitor enrollment has its own CSRF cookie/header and device-bound context. SCIM uses connector bearer authentication instead of browser cookies/CSRF. Browser access is same-origin, without permissive CORS.

Own password change verifies the current password, revokes other sessions, and rotates the current session/cookies. Logout revokes the current session and expires cookies. Disabled/deleted Accounts, disabled identities, and expired/revoked sessions cannot authenticate. Reset-required password credentials block that password method.

## Challenges and administrative recovery

Invitations, email verification, password recovery, and PIN setup store keyed code digests with expiry, attempt count, used/cancelled state, and delivery outcome. Codes permit at most five failed attempts. Issuance and completion also have database-backed rate limits. `PASSWORD_RESET_TTL` defaults to thirty minutes and is used by setup/recovery challenges. Successful redemption is single-use and transactional with the credential/verification change and audit. Password challenges are addressed to the password identity. PIN challenges are delivered to the Person's email (the login email) when there is one, but do not require it.

Anonymous recovery returns the same empty HTTP 202 response for known, unknown, disabled, and rate-limited Accounts and delivery failures. Malformed requests and infrastructure failures use the documented error responses. Responses do not expose Account existence, codes, or links. Database work and synchronous SMTP delivery can affect latency; timing equality is not guaranteed. No artificial delay or asynchronous infrastructure is used. Configured SMTP delivers challenges; delivery failure is recorded without storing provider messages or secrets. An authorized administrator issuing an invitation/reset can receive its one-time URL when mail is disabled; PIN setup also returns that manual URL whenever the Person has no email. Anonymous requests never get that fallback. Challenge and one-time-secret responses use `Cache-Control: no-store`.

Self-service reset works for every enabled Account with an enabled login email, including Accounts that never set a password. Emailed reset, invitation, email-verification, and PIN-setup links carry the email address and one-time code in the URL fragment (`/reset-password#email=...&code=...`), which browsers never send to the server; the page reads the fragment once and removes it from the address bar. The code is also printed in the mail. Delivery outcomes are stored on the challenge (`sent`, or `failed` with `mail_disabled` or `provider_error`) and failures are logged with the request and challenge IDs only.

All system mail is sent as multipart/alternative (plain text plus a table-based, inline-styled HTML layout using the branding application name, brand colour, logo, organization, and legal links). The shared layout lives in `backend/internal/notifications` (`RenderBranded`, `Service.SendBranded`) and `mail.Message` supports attachments (multipart/mixed).

The older opaque-token reset completion endpoint remains supported alongside email/code recovery. Its token digest and expiry are checked transactionally. Administrative password set/reset permissions remain distinct; administrative reset requires subsequent credential setup and revokes sessions. The CLI `reset-password` repairs only the local credential selected by an existing password login email; it never derives a password identity from a PIN username. `recover-master` is reserved for installations without an enabled master. See [operations](operations.md).

No passwords, hashes, codes, tokens, cookies, authorization headers, or request bodies belong in logs or audit metadata. Mutations write minimal audit events in the same PostgreSQL transaction. OIDC and SMTP secrets use the ordered application keyring; production also requires stable challenge-HMAC and PIN-pepper keys. Retention gaps and remaining identity-lifecycle questions are listed in [known limitations](known-limitations.md).
