# Machine logbook

The machine logbook records machine usage, material stock, pricing, charge-source traceability, and operational reporting for one makerspace. It is one backend feature package, **internal/machinelogbook**, so job confirmation, stock deduction, price capture, and audit events share a PostgreSQL transaction.

## Catalog and parties

Processes and machines are versioned. A machine status is administrative only: **active**, **maintenance**, or **retired**. Availability is derived separately and never stored (see [Work items and machine activity](#work-items-and-machine-activity)). Printer connector state is shown separately. Referenced processes and machines are retired instead of deleted.

### Processes

A **process** is what a machine does: laser cutting, embroidery, FDM printing. Processes are an editable catalog (Settings, `/processes`; migration 00088 turned the former machine types into processes and removed the fixed list `fdm_printing`, `embroidery`, `uv_printing`, `laser_cutting`, `vinyl_cutting`, `other`). Every machine has exactly one process, and the process carries the runtime price, the trainings that cover it, the materials that fit and the measures a run records. Processes are versioned and deactivated instead of deleted.

A process has a name (unique ignoring case), an **integration** and a list of **measures**:

- `integration` is `none` or `fdm_printer`. Only machines whose process has the `fdm_printer` integration have a printer setup (printer profile, spool inputs, connector assignment): `PUT /machines/{id}/printer` and `PUT /machines/{id}/printer/setup` answer `409 machine_not_fdm_printing` for any other machine (the code predates the catalog and stays for clients). Everything FDM-specific (setup, wizard, connectors, spools, artifacts, live status, reported grams) is gated on the integration in the frontend as well. Changing the integration is allowed; existing printer profiles and runs stay.
- `measures` are counted facts of a run that are not material, each with a `key` (`^[a-z][a-z0-9_]{1,39}$`, unique within the process), a `label` (1 to 60 characters), a `unit` (1 to 20) and a `blockSize` (at least 1; rates are per block). At most 20 per process. Migration 00088 gave every former embroidery type `stitches` (Stitches, stitch, 1000).

`GET /processes`, `POST /processes` (`name`, `integration`, optional `measures`) and `PATCH /processes/{id}` (`expectedVersion` plus any of `name`, `active`, `integration`, `measures`) need `machines.read` or `machines.manage`. A given `measures` list replaces the stored one (order kept); an omitted one keeps it. Removing a measure that a pricing rule (active or not) or a stored run still uses answers `409 measure_in_use` and changes nothing. Every write is audited as `process.created` or `process.updated` (older rows keep `machine_type.*`). A `Machine` embeds its process with the measures.

Runtime is billable on every machine; a group that should not pay for time gets a 0 EUR/h rule.

### Units

Material units belong to one **dimension** (migration 00107): mass (`g`, `kg`), length (`mm`, `cm`, `m`), area (`cm2`, `m2`), volume (`ml`, `l`) and count (`piece`). A material type's unit is its **reference unit**: material and variant rates and statistics are per that unit, and the type's `dimension` follows from it. An article counts in any unit of its type's dimension (default: the type's unit); a piece article may name its piece with a `countLabel` (1 to 20 characters, for example Sheet or Pair). Units convert only within a dimension (`machinelogbook/units.go`, SQL `material_unit_factor`), rounded to six decimals. Filament types and articles stay `g`. The frontend shows `cm2`/`m2` as cm²/m² and `piece` as pcs or the count label. Unit lists are validated in `machinelogbook`, the OpenAPI `MaterialUnit` enum and the CHECK constraints of `material_types`, `materials`, `pricing_rules` and `machine_run_usages`.

**Changing units.** A type's unit can change to another unit of its dimension at any time; its material and variant rates are converted in the same transaction. A unit of another dimension needs an unused type (no material, pricing rule or run usage; 409 `material_type_unit_in_use`). An article's unit can change within the dimension at any time: in one transaction the ledger quantities and unit costs (the value stays), the balance, package size, low-stock threshold, its `stock_article` rates and its run usages are converted, audited as `material.unit_converted`. A unit of another dimension answers 422 `material_unit_mismatch`. Pricing snapshots and order items keep the unit they were captured in. Run usages store their own unit (`machine_run_usages.material_unit`).

### Materials by process

`material_type_processes (material_type_id, process_id)` lists the processes a material type can be consumed on; the kind of the type decides the list (see [Articles and kinds](#articles-and-kinds); `POST /material-types` takes `processIds`, `PUT` keeps them when omitted, unknown ids answer 422). A filament type given no processes serves every active process with the `fdm_printer` integration at that moment. For **new** makerspace usages (manual job, added run, usage replacement) the backend refuses material whose type does not include the machine's process: `422 material_process_mismatch`. Materials a run already uses stay allowed when its usage list is replaced, customer material (free text) is never checked, and recorded (connector) usages are not checked. The frontend picker lists only active materials of fitting types, plus the material of the row being edited.

### Run measures

`machine_run_measures (run_id, measure, value)` stores counted facts of a run (exact whole number, `bigint`, at least 0). The keys come from the measures of the machine's process. Runs and jobs expose `measures` (a map `{<measureKey>: integer}`; a job sums its runs that are not replaced). Manual run create/add (`measures` on the run input) and `PATCH /machine-runs/{id}` (manual runs; replaces the stored set when given) accept them; a measure the machine's process does not define answers `422 run_measure_unsupported`, a malformed key or a negative value `422 validation_failed`. Moving a job to a machine whose process cannot record its measures is refused the same way.

### Measure pricing

Pricing rule kind `machine_measure` prices a measure per process: `processId`, `measure`, the stored `blockSize` (taken from the process measure, 1000 for stitches) and the rate per block, kept exactly (`numeric(20,6)`). The amount is `value x rate / blockSize` (multiplied first, so whole blocks are exact) and only the job total is rounded half-up to cents: 12,400 stitches at 0.50 per 1000 give 6.20. Rules are only accepted for processes that define the measure, and one active rule per group, process and measure. A job's snapshot captures a `machine_measure` entry for every measure its machine's process records (rate, block size and unit of the process measure) plus any measure that already has a value. A value without a rate makes pricing **incomplete**; an explicit zero rate is free; a measure that first gets a value after the snapshot was taken (for example after the process gained the measure) triggers a new snapshot of the same group.

### Printer setup

A printer profile holds the printing switch, an optional model (`bambu_h2d`, `bambu_x1c`, `prusa_core_one`, `generic`; the frontend keeps the unit and slot templates per model), the number of nozzles (`nozzleCount`, 1 to 8, default 1), spool input units and their slots. A unit may name the nozzle it feeds (`left` or `right`), and every unit and slot carries the 1-based `nozzleIndex` it feeds (default 1; migration 00099 set units that named the right nozzle to 2 and gave H2D profiles two nozzles). Core only stores the nozzle numbers; nothing else depends on them yet. The machine wizard's Spool inputs step sets the number of nozzles and, with more than one, the nozzle each unit feeds (on a two-nozzle printer nozzle 1 is the left and nozzle 2 the right one); every slot of a unit is saved with the unit's nozzle.

**Printer setup page** (`/workshop/machines/{machineId}/printer`; the former `?tab=printer` link redirects). It shows what needs attention (spools the printer reports in a slot without a spool in Core, a degraded or disconnected connector), a **Connection** card (state, connector, adapter, serial number and address of Bambu printers, firmware, last heartbeat; Edit and Test connection open the connection step of the wizard) and a **Recording** card with switches for the printer profile (disabling asks first), automatic run recording (the machine's `automaticCollectionEnabled`; turning it off clears the external identifier), auto-mounting RFID spools and relaying the camera to signage (both Bambu adapters only, saved on the connector assignment with `printer_connectors.manage`). **Spool slots** lists every unit with the nozzle it feeds and per slot what the printer reports, the spool in Core and the actions: **Unmount**, **Mount** (an unmounted consumable spool) or, for a loaded spool Core does not know, **Register** (`inventory.articles.manage`): the dialog suggests the filament article of the reported type and colour, takes the net weight from the reported remaining percentage, books it from loose stock or as a purchase (`POST /filament-spools`), tags the spool with the RFID tag the printer read and mounts it in the slot (`printer_slots.assign`). **Printer events** lists the latest errors of the printer with their meaning and run.

`PUT /machines/{machineId}/printer/setup` (`machines.manage`) saves all of it atomically. The body is the _desired state_, not a patch: `expectedVersion` (the profile version, `null` or `0` when the machine has no profile yet), `enabled`, `model`, `nozzleCount` and the ordered `inputUnits`, each with its ordered `slots`. An omitted `nozzleCount` or `nozzleIndex` keeps the stored value; a new unit feeds nozzle 1 and a new slot its unit's nozzle. Every index must be at most the count (`422 validation_failed`). Entries with an `id` update the existing row, entries without one are created. In one transaction Core

- creates the profile when it is missing, otherwise requires `expectedVersion` to match (`409 stale_write` when it does not) and bumps the profile version;
- renumbers the active units and the active slots of each unit `0..n-1` in the given order;
- **retires** slots that are not listed (status `retired`, identifier cleared, moved behind the active ones) and **disables** units that are not listed (`enabled=false`, identifier cleared, their slots retired). Nothing is deleted, because mounts and print history reference these rows. A listed id that was retired or disabled earlier is revived;
- refuses to retire a slot with a mounted spool (`409 slot_occupied`) and rolls everything back;
- rejects two units, or two slots of one unit, with the same printer identifier up front (`422 duplicate_external_identifier`), rejects ids that do not belong to this machine (`422 validation_failed`), and returns `409 duplicate_external_identifier` should the unique index still fire;
- bumps the configuration revision of the connector assigned to the machine when `enabled` changes, because the printing switch is part of the connector configuration;
- writes one audit event `printer_profile.setup_saved` in the same transaction.

Requested slot statuses are `available` or `unavailable`; `retired` only results from omitting a slot. Unchanged rows keep their version. The existing single-row endpoints for units and slots keep working. `GET /machines/{machineId}/printer/live-status` (`machines.read`) returns the latest connector snapshot (see the [printer connector](printer-connector.md#live-status)).

Organizations are versioned billing parties with the type **company**, **institute**, **association**, or **other**. An identified job customer is either a Person or an Organization, represented by two mutually exclusive nullable foreign keys. Jobs created before counter sales were removed may still have neither. Operators are People with enabled Accounts.

Organizations also carry an invoice address (address line, postal code, locality, ISO country code), an invoice contact name and an optional contact email; empty strings mean "not set". `PATCH /organizations/{id}` leaves omitted detail fields unchanged and clears a field when given an empty string. The purchase-order requirement stays in `organization_invoicing_requirements` (see [Orders](orders.md)) and is read and written through `/organizations/{id}/invoicing-requirements`; the organization page uses both endpoints. People can be associated with an organization (`organization_members`, unique per pair, removed with either side). Membership is informational: it never restricts who may bill an organization. It feeds the overview on the organization page and the job form, where choosing a person who belongs to exactly one active organization offers a one-click "Bill to <organization>" (the billing-party search returns `memberOrganizations` for people; nothing is switched automatically). Organizations are created, edited and assigned a pricing group on the **Directory › Organizations** pages (`/organizations`, `/organizations/:id`), not in Settings. Customer and operator searches return only identifiers and display names needed for assignment.

Person references use ON DELETE SET NULL. Hard-deleting a Person therefore removes their PII without deleting non-PII machine, timing, usage, price, or inventory facts. Jobs do not retain person-name snapshots. Organizations referenced by machine jobs (including deleted ones), orders or invoice requests are deactivated instead of deleted: `DELETE /organizations/{id}` (body `{expectedVersion}`, `organizations.manage`) answers 409 `organization_in_use` for them, because those foreign keys are ON DELETE SET NULL and would otherwise silently erase history. An unreferenced organization is hard-deleted together with its members, pricing group assignment and invoicing requirements (ON DELETE CASCADE) in one transaction with an `organization.deleted` audit event that carries no field values; a stale version answers 409 `stale_write`. The organization page offers this as a danger action with a confirmation dialog.

## Jobs and runs

A **job** is the billable record of work on one machine. Jobs have an application-generated UUIDv7 and a sequence-backed display identifier such as **J-2026-000001**; sequence gaps are expected. A job consists of one or more **runs**. A **run** is one period of work on the job's machine. It is either **manual** (entered by staff) or **recorded** (reported by a machine connector, such as a [printer connector](printer-connector.md)). Runs have display identifiers such as **R-2026-000001**. The model covers every process, including 3D printers, lasercutters, and embroidery machines. Former prints are recorded runs; prints no longer exist as a separate concept. Times are stored as UTC timestamptz.

**Name.** A job has an optional title (at most 200 characters). The display name is the title, else the job number. The J-number stays the stable identifier.

**Billing facts.** A job keeps its customer, operator, title, notes, pricing, and price adjustment. Start, end, and runtime are derived from the job's runs; runtime is the sum of the runs' runtimes. Material usage belongs to runs.

**Status and outcome.** A job is **running** while any of its runs runs: a manual run until its planned end, a recorded run as the connector reports it. Otherwise the job's outcome is derived from its runs' outcomes. If all runs are successful, cancelled, or failed, the job takes that outcome; a mix gives **partial_failure**; while a run has no outcome, the job is **unknown**. Staff can set an outcome override, which takes precedence. Outcomes do not decide whether material consumption is retained.

**Runs and material.** Staff add further runs with **Add run**, for example for reprints. Material usage is a set of typed material/quantity rows on a run. Quantities are in the article's unit (see [Units](#units)). Filament usage records makerspace or external ownership, optional physical Spool attribution, and an actual or estimated quantity basis. External filament does not consume stock or add a makerspace material charge. The module deliberately does not provide a generic metric/EAV store.

**Recipient's own material.** A usage with ownership `external` may name an article (`materialId`), a material type (`materialTypeId`) and a short `label` (up to 120 characters), all optional: "PLA, recipient's own, Prusament Galaxy Black" is the PLA type with that label (migration 00097 added `machine_run_usages.material_type_id`; the label is stored in `external_material_name`, and the older `externalMaterialName` field is accepted as an alias). An unknown type, or an article of another type, answers `422 validation_failed`; makerspace usages refuse a label or type. Responses carry `label`; `materialName` is the label, else the article's or type's name, else "Own material", and the unit comes from the article or type (grams without either). Own material is never consumed from stock and never priced.

**Manual runs.** A manual run's material is always measured: the server stores `quantityBasis: actual` for every usage of a manual run (create, add run, usage replacement) whatever the request says; recorded runs keep estimated or actual. `startsAt` is optional on `ManualRunInput` and means now when omitted; a start more than a minute in the future answers `422 validation_failed`, and the end must lie after the start.

**Recorded runs.** A recorded run may stay unassigned to any job. Staff create a job from a recorded run, or attach it to an existing job on the same machine, also while it is still running. Attaching can replace the job's manual runs: they are kept as "replaced" for history, and their material is reversed. Detaching a run keeps the run's material with it. If it was the job's last run, the job gets a manual copy without material.

**Machine-reported material.** When a recorded run ends, its machine-reported material is consumed automatically, also without a job, and shown as "From machine". A later report revision replaces it without double counting. The outcome is set from the machine's final state ("From machine") until staff change it. Connector-driven changes reprice the job and are audited with the system actor, with the connector ID in the audit metadata. Running jobs cannot be added to orders. Machine-reported consumption uses the ledger kind `machine_run_consumption`; the schema change is migration 00041. A reported line fed by two or more spools during the print (AMS refill, reloaded tray, new RFID tag; see [printer connector](printer-connector.md#reliable-event-delivery)) is stored with its `segments` (`machine_run_reported_usage_segments`, migration 00105) and no spool of its own: each segment is resolved at its `startedAt` by the same rules as a line (historical slot mount and exact NFC tag; disagreement stays unresolved) and booked on that spool with its own quantity, so segments on spools of different articles book and price each article; the run then has `materialChangedDuringRun`. Lines or segments that resolve to the same spool are one usage. A segment without spool or quantity is not booked. Staff complete such a run by replacing its usage (`PUT /machine-runs/{runId}/usages`, `machine_jobs.edit`, the run's material dialogs): the list they save, the booked segments plus the missing spool and grams, replaces the machine's usage and is never overwritten by a later report.

**Concurrency.** Operations lock the job before its runs. A rare conflict returns 409 `retry_conflict`, and the client retries.

Every new job has a customer; counter sales were removed. Jobs that exist without a customer (from the former counter sales) stay editable.

Confirmed corrections use optimistic concurrency. Source and external identifiers remain immutable. Usage replacement creates compensating inventory transactions; immutable ledger history is never rewritten. A finalized Order does not lock operational job corrections: its immutable item snapshot remains unchanged and the UI/API reports source changes. Omitted customer on a factual correction preserves the current identity, including a job without customer.

Legacy job billing fields and the billing endpoint were removed with migration 00028. The charge flow is **Machine Job → Order Item → Order → Payment or external wiRef invoicing**. [Orders](orders.md) describes frozen charge snapshots, and full reversal/replacement.

**Deleting a pricing rule.** `DELETE /pricing-rules/{pricingRuleId}` (`pricing.manage`, body `{expectedVersion}`, 204) removes a rule of any kind and state for good: 404 for an unknown rule, 409 `stale_write` for an old version, audited as `pricing_rule.deleted` in the same transaction. Pricing snapshots are unaffected: `machine_job_pricing_snapshot_rules.source_rule_id` is `ON DELETE SET NULL`, so existing entries keep their copied rate and label, lose only the pointer, and a recalculation from the snapshot charges the same amount. Only a new snapshot (re-pricing a job) sees the rule missing.

## Pricing snapshots

**Pricing page.** The rates table (Sales & payments › Pricing, `pricing.read`; changes need `pricing.manage`) has one column per active group and four row groups: machine time per hour, measures per block, materials used on machines per unit (material types with machine use, each expandable into its variants: a variant row shows its own rate, or the type's rate muted as inherited, and a cell sets or clears the variant's rule through the same rate dialog), and articles sold from stock per unit (the active articles of material types without machine use, by article number; articles of machine-use types sell at their type's rate and have no row). A cell opens a rate dialog that creates or updates the rule; for an article, emptying the field deactivates its `stock_article` rule. An article without any price shows "No price" and cannot be sold to that group. Missing rates are counted for machine time, measures and materials only.

Pricing groups are independent of Roles; Roles are mapped to groups in `role_pricing_groups` (`GET`/`PUT /pricing-role-groups`, `pricing.read`/`pricing.manage`; migration 00050). The mapping holds each role at most once with a unique positive `priority` (the larger number wins) and is replaced atomically. The group of a job resolves in this order, in `resolvePricingGroup` (also used for jobs planned from print artifacts):

1. the explicit group on the create, reassignment or correction request (a manual override; an inactive group is refused with 409 `pricing_group_inactive`);
2. the group of the organization the job is billed to (`organization_pricing_group_assignments`);
3. for a person customer, the group mapped to their highest-priority role;
4. the one active global default.

Inactive mapped groups are skipped (the next role, then the default applies). An organization without a group, and a person without a mapped role, use the default. The per-person pricing group assignment (`person_pricing_group_assignments`) was dropped in migration 00050 and `PUT /billing-party-pricing-group` now accepts organizations only; use the role mapping or the explicit group on the job instead. Price adjustments on a job are unchanged.

If none resolves, manual creation fails until a group is selected. A group contains exact-decimal machine-runtime rules per process/hour, measure rules per process (see [Measure pricing](#measure-pricing)) and material rules per **material type** or per **variant** of a type (a rate per reference unit of the type, converted to the article's unit when it prices a usage; see [Material rate resolution](#material-rate-resolution)). A job's pricing snapshot stores each material rate that prices a usage with its label, a selector text, the unit and a `material_type_id`; usages match snapshot rules by article, variant and type (below), so renaming or recolouring never changes a captured price. Snapshots taken before migration 00046 keep their category text and were backfilled with the matching type. Missing matched rules make pricing **incomplete** and leave the calculated total unset. An explicit zero rate is intentionally free.

### Material rate resolution

One order decides the rate of an article in a pricing group, for machine run usages, price quotes, sales from stock (order items) and `Material.prices` alike: (1) the article's own active `stock_article` rule, else (2) the active `material` rule of the article's variant, else (3) the active `material` rule of its type. The first that exists wins; variant and type rates apply to types with `machineUse` and are converted from the type's unit to the article's unit. An article without a variant, or whose variant has no rule of its own, takes the type's rate. The source is reported as `MaterialPriceSource` (`stock_article`, `material_type_variant`, `material_type`). `PriceQuoteMaterial.variant` names the article's variant.

**Rules.** `materialTypeVariantId` on `PricingRule`, `CreatePricingRuleRequest` and the update request is optional on `material` rules and forbidden on every other kind; null is the type's own rate. The variant must belong to `materialTypeId` (422 `material_type_variant_mismatch`). There is at most one active material rule per pricing group, type and variant, the null variant counting as one slot (partial unique indexes `pricing_rules_active_material_type_idx` and `pricing_rules_active_material_variant_idx`, which replace `pricing_rules_active_material_idx`). `PricingRule` also returns `materialTypeVariantName`.

**Behaviour change: machine runs honour an article's own rate.** A run usage used to be priced by its type's material rate only; it is now priced like a sale from stock, so a `stock_article` rule of the used article (which before applied to sales only) or a variant rate takes precedence over the type's rate. Stored snapshots are not rewritten; the new order applies to snapshots captured from now on.

**Snapshots.** `machine_job_pricing_snapshot_rules` gained `material_id` and `material_type_variant_id` (historical copies without foreign keys, so a later purge or deletion never makes an entry broader) and the kind `stock_article`. Per usage the snapshot records the rule that priced it: a `stock_article` entry with `material_id` and the article name as selector, a `material` entry with `material_type_variant_id` and the type and variant name as selector, or the type's `material` entry. A usage finds its entry in the same order (article, variant, type; a rate captured in another unit of the same dimension is converted); a missing entry still covers the usage as "no price at capture time". Entries of snapshots taken before migration 00103 are type entries.

Every confirmed job receives an immutable snapshot revision containing the group name, EUR currency, capture time, matched rate and unit, missing-rule markers, and source rule IDs for traceability. Customer or machine-type correction creates a new revision and retains older revisions. Timing and usage corrections recalculate against the active snapshot. The exact component sum is rounded half-up to cents only at the final total.

The calculated amount and the price adjustment are separate. An adjustment (`PUT`/`DELETE /machine-jobs/{id}/price-adjustment`, migration 00036 replaced the former fixed override) has a kind, value, reason, actor, and time and never alters the calculation. Kinds: **fixed** (EUR), **discount_percent** (0-100], **discount_amount** (EUR), and **multiplier** (factor up to 100). Relative kinds are re-applied whenever the calculated price changes, for example after a run or usage correction or a connector-driven change. The **effective price** (stored, rounded half-up to cents) is the adjusted amount when an adjustment exists and otherwise the calculated amount. Adjustments need `machine_jobs.override_price`.

## Inventory and valuation

Materials (articles) are versioned catalog records with a **material type**, unit, optional colour (name and `#RRGGBB` code), active state, and optional low-stock threshold.

**Material types** (`/material-types`, migration 00046) are the level a price attaches to: PLA, PETG, TPU 95A and so on. A type has a name (unique ignoring case), a reference unit (see [Units](#units)), the processes it can be consumed on, an active flag and a version. Reads need `inventory.read`, writes `inventory.articles.manage`; every write is audited in its transaction. An article's unit is any unit of the type's dimension (422 `material_unit_mismatch` otherwise); material pricing rules keep the type's unit through a composite foreign key that follows a unit change (see [Changing units](#units)). Deleting is a hard delete that takes the type's variants and all its pricing rules (active or not, in every group) with it in the same transaction; only a material that references the type, deleted ones included, blocks it with 409 `material_type_in_use`, and the type should then be deactivated, which keeps existing materials and rules but refuses new ones. The `material_type.deleted` audit event records `countPricingRulesRemoved` and `countVariantsRemoved`; job pricing snapshots keep their copied rates.

**Colour** is captured only on the material: `colorName` (free text, up to 80 characters) and `colorHex` (`^#[0-9A-F]{6}$`, upper case). Spools, jobs and runs only display it. Colours from print files ("Detected in file") and from the printer's AMS ("Reported by printer") are detected values used for comparison only; the printer setup shows a hint when a mounted spool's material colour is clearly different (RGB distance above 80) from the reported tray colour, and the material form can take the reported colour with one click.

**Migration 00046.** Every distinct legacy (category, unit) of a material or material pricing rule becomes one type. A category of up to four characters is upper-cased ("pla" becomes "PLA"), longer ones use initcap ("filament" becomes "Filament"); a category used with several units gets the unit appended ("Sheet (m2)"). The old colour text becomes the colour name, the colour code stays empty and can be added later. Rates are unchanged. `materials.category` and `materials.color` and `pricing_rules.material_category` are dropped; the down migration restores category from the type name (lower case, without a unit suffix) and the colour from the colour name.

### Articles and kinds

Every material type has a **kind** (migration 00056): `filament` (unit `g`, processes with the `fdm_printer` integration, spools), `consumable` (at least one process) or `part` (no process, so `material_process_mismatch` keeps it out of every machine run; the type acts as the part's category). `kind` is required on create; it can change only while no material uses the type (409 `material_type_in_use`), and an article cannot move to a type of another kind (409 `material_kind_change`). Existing gram types serving only FDM printing became `filament`, all others `consumable`.

An article adds `variant` (one of the type's variants, see below), `manufacturer` (≤150), `packageSize` (quantity per roll or bag), `storageLocation` and `notes` (all optional) to the former fields; `kind` is read from the type. Every article has a `displayId` `A-0001` (migration 00095; assigned on creation from a sequence, backfilled by creation order) and `attention` flags (`low_stock` while the quantity is at or below the low-stock threshold).

**Variants** (migration 00103). A filament or consumable type carries a list of variants (PLA: Basic, Matte, Silk …) in `material_type_variants`; `MaterialType.variants` returns them by name, each as `{id, materialTypeId, name, materialCount, pricingRuleCount}` (articles including deleted ones, active pricing rules). Names are trimmed, 1–80 characters and unique per type ignoring case (409 `material_type_variant_exists`); parts have none (422 `material_type_variant_not_allowed`, also for an article of a part that names a variant, which is ignored). An article picks its variant from its type's list: `variantId` (read-only) and `variant` (name) on `Material`; the create and update requests take the name only, matched ignoring case after trimming, and a name the type does not have yet creates the variant in the same transaction (audited as below). `materials.variant` stays the denormalised name, written together with `variant_id` (a check keeps both set or both empty).

- `POST /material-types/{materialTypeId}/variants` (`{name}`, 201), `PATCH …/variants/{variantId}` (`{name}`) and `DELETE …/variants/{variantId}` (204) need `inventory.articles.manage`; the type is share-locked and an unknown type or variant answers 404.
- **Rename** changes the variant row and the `variant` text of all its articles in one transaction. An article whose name is the one generated from type, variant, colour and manufacturer is renamed with it (a typed name, or a generated one that would no longer fit, stays). Spool labels are fixed when a spool is registered and keep the old name.
- **Delete** is refused with 409 `material_type_variant_in_use` while any article (deleted ones included) or any active pricing rule references the variant. Its inactive rules (cleared rates) are deleted in the same transaction before the variant row, because the database restricts the reference.
- **Audit** on the material type, in the mutation's transaction: `material_type.variant_created`, `material_type.variant_renamed` (metadata `variantId`, `countArticles`, `countArticlesRenamed`) and `material_type.variant_deleted` (metadata `variantId`, `countPricingRulesRemoved`); changed fields `variants`.
- The configuration import resolves variant names through the same lookup, so an unknown name adds the variant (see [configuration-transfer.md](configuration-transfer.md)).

**Type codes and machine use** (migration 00095). A material type has a `code` (1–12 upper-case letters or digits, unique ignoring case, 409 `material_type_code_exists`; defaults to the first word of the name, numbered when taken) used in spool labels, and `machineUse`: materials of the type are used in machine runs and priced by `material` rules. Filament types always have it; parts default to false. A type without machine use refuses `material` pricing rules (422 `material_type_not_priced`) and new run usages (422 `material_process_mismatch`); machine use cannot be turned off while active material rules price the type.

**Sale prices** (migration 00095 removed `salePrice`). An article sold from stock is priced per pricing group by a `stock_article` rule (`materialId`, rate per unit of the article, one active rule per group and article); without one, a machine-use article uses the `material` rate of its variant, else of its type (see [Material rate resolution](#material-rate-resolution)). `GET /materials` returns these as `prices: [{pricingGroupId, pricingGroupName, rate, source, pricingRuleId}]` for every active group that has a price; `source` is `stock_article`, `material_type_variant` or `material_type`. An order item of an article takes the price of the customer's pricing group (organization group, else the highest-priority role group, else the default group) unless a unit price is given; without a price it fails with 422 `article_price_missing`. Former sale prices became `stock_article` rules in every group. `GET /materials` filters by `kind` and searches (case-insensitive substring) name, type, variant, manufacturer, colour name, storage location and notes. The name is optional for filament and consumables and then generated as "<Type> <Variant> · <Colour> · <Manufacturer>" without missing parts ("PLA Basic · Black · Bambu Lab"); parts need a name. Names stay unique ignoring case: a taken name answers 409 `material_name_conflict` with `details.materialId` of the existing article. Filament articles always have a diameter (default 1.75 mm); other kinds refuse one.

Purchases take an optional `reference` (≤200, order or invoice number), stored in `inventory_transactions.purchase_reference` and covered by the immutability trigger.

### Receiving stock

`POST /inventory/receipts` (`inventory.receive`, plus `inventory.articles.manage` for a newly described article; spool placements also `filament_spools.manage`) books `packageCount` × `packageSize` (default: the article's package size) for an existing article (`materialId` + `expectedInventoryVersion`) or a new one described inline (`material`, created in the same transaction), with total price (2 decimals), supplier, reference, note and a date that is not in the future. Non-filament articles always produce one purchase row. Filament placements are described in [filament-printing.md](filament-printing.md#receiving-filament). Everything commits in one transaction with the audit event `inventory.receipt_recorded` (plus `material.created` for an inline article); the response carries the article, the spools and the ledger rows. `GET /inventory/suggestions` (`inventory.read`) lists up to 50 distinct variants (optionally per `materialTypeId`), manufacturers, suppliers and storage locations, most frequent first.

Order snapshots keep the JSON key `category` for a usage's material; it now carries the material type name. **inventory_transactions** is an immutable ledger with purchase, machine-run consumption, manual consumption, adjustment, disposal, and spool-transfer entries, plus `order_sale` (negative) and `order_sale_reversal` (positive) entries that Orders write for sold articles (see [orders.md](orders.md)). Both carry `order_item_id`, which may only be detached when the order item is deleted, and are unique per item. The ledger read model (`InventoryTransaction`, material and spool ledgers) returns `orderId` and `orderReference` for these two kinds, joined through `order_item_id`; it needs only `inventory.read` and exposes no customer data (the frontend links the reference to `/orders/:id` only with `orders.read`). `recentConsumption` on materials (30 days, used for stock hints) counts consumption, corrections and disposals plus order sales net of their reversals, never below zero. Machine statistics are unchanged: sales are not machine use, so the material cost and loss figures above ignore `order_sale` and `order_sale_reversal`. Order sales consume only unassigned stock; the machinelogbook `Service` exposes `SellFromStock` and `RestockOrderSale` for that, taking the caller's transaction. The material balance is maintained transactionally with quantity, inventory value, weighted-average unit cost, and an inventory version.

Gram-denominated filament Materials may define a diameter and contain physical Spools. Spool balances are derived from the same ledger through attributed transactions and zero-value transfers, while the Material exposes assigned and unassigned quantities. See [Filament spools and generic printer integration](filament-printing.md) for spools, labels, retiring and receiving filament.

### Inventory recycle bin

Migration 00096. `GET /inventory/recycle-bin` (`inventory.read`) lists, newest first and at most 500 each, deleted articles (with stock, spool count, time and actor), retired spools of articles that are not in the bin, and deleted ledger entries.

- **Articles.** `DELETE /materials/{id}` (`{expectedVersion}`, `inventory.delete`) sets `deleted_at`/`deleted_by`; the article, its spools (mounted ones are unmounted), its prices and its stock leave every list, picker, total and receipt, and stock movements on it answer 409 `material_in_bin`. `POST /inventory/recycle-bin/materials/{id}/restore` brings it back unchanged; `DELETE …/purge` is a genuine hard delete of the article with its balance, spools, identifiers, mount history, `stock_article` rules and every ledger entry. Run usages keep the article name and unit (`material_name`, `material_unit`) and lose the link; order items keep their description. Audited as `material.deleted|restored|purged`.
- **Ledger entries.** `DELETE /inventory/ledger/{id}` (`{expectedInventoryVersion}`, `inventory.ledger.delete`) takes the entry's quantity and value out of the balance and its spool's remainder; a change that would make stock, a spool or loose stock negative answers 409 `insufficient_stock`, `insufficient_spool_stock` or `insufficient_unassigned_stock`. Run usages and order items are not touched, so a later usage correction books against what is left in the ledger. Restore adds the effect back; purge hard-deletes a deleted entry. Audited as `inventory.transaction_deleted|restored|purged`.
- **Spools.** Retired spools are restored or purged as described in [filament-printing.md](filament-printing.md#retiring-restoring-and-purging).

The ledger stays immutable otherwise: the trigger allows deletes only inside a purge transaction (`makerspace.inventory_purge`) and allows setting `deleted_at`/`deleted_by`.

Every balance mutation locks material rows in UUID order, checks **expectedInventoryVersion**, prevents negative stock, writes its ledger row, updates the balance, and writes audit data in the same transaction. Multi-material job consumption is all-or-nothing.

Purchases add their total acquisition price and recalculate weighted-average cost. Outgoing consumption and disposal record the current average cost. Positive corrections of loose stock use the current average; when none exists, the correction requires an acquisition unit cost. Positive spool corrections (weighing) use `acquisitionUnitCost` when one is sent, else the unit cost of the spool's own purchase, else the current average, which is 0 for existing stock without a known price; they are never refused for a missing cost. Marking a material empty writes one negative adjustment for the locked current quantity. No correction edits historical transactions.

## Work items and machine activity

Work item lists carry a `consumption` summary per item (material summed per material type and unit, plus measures); the frontend writes it in each unit ("12,400 stitches · 0.4 m Stabilizer", "3.20 ml UV ink · 180 cm² DTF paper"). FDM runs and jobs that only used grams keep their per-material text.

`GET /machine-logbook/work-items` lists every job plus every recorded run not assigned to a job in one paginated table (`machine_jobs.read`). The unified status is **running**, **unassigned** (an ended recorded run without a job), **needs_outcome** (outcome still unknown), or the recorded outcome. The `run` filter separates **manual** from **recorded** items. Filters cover search, status, machine, material, billing state (jobs only), customer, operator, and a start-time range where `to` is exclusive. Billing states are on_order, order_outdated, not_on_order, price_incomplete, and pending.

The `search` of the work-item table is a case-insensitive substring match. For a print it covers the display ID, file name and machine name; for a job the display ID, name, notes, machine name, recipient (person or organization) name, operator name and the display IDs and file names of its prints. `GET /machine-runs` searches the run display ID, file name and machine name, the display ID and name of its job, the material name and spool display ID of the reported spool, and the job's recipient and operator names. `GET /machine-jobs` (the job pickers) searches the job display ID, name, notes, machine name, recipient, operator, used material names and the display IDs and file names of its runs. `GET /machines` searches the machine name, machine type and external identifier. Search terms never match matriculation numbers.

`GET /machine-logbook/machine-activity` returns one entry per machine with derived availability, the current running job or running run, connector state, and the last job start. `current` is included only for callers with `machine_jobs.read`.

`GET /machine-logbook/overview` returns the existing counts plus running now (running jobs and running unassigned recorded runs), machine names, needs outcome, `unassignedRuns`, billing issues (incomplete pricing or outdated order), and up to six active items. The fields that expose jobs are null without `machine_jobs.read`.

`GET /machine-logbook/statistics` takes `from` and `to` dates, with `to` exclusive. It returns totals and `previousTotals` for the period of equal length ending the day before `from`, per-month charges, material cost and losses, runtime buckets (weekly up to 92 days, otherwise monthly), material usage and cost by material type (`materialUsageByType`, `materialCostByType`), and per-machine figures. Material cost is the inventory value consumed by jobs and manual consumption net of job corrections; losses are the inventory value removed by disposals and by negative stock corrections other than job corrections. Runtime of a running job counts until now.

It also returns:

- `usageByWeekdayHour`: machine minutes and the number of runs per hour of the week (Monday = 0) in the makerspace's time zone (`MAKERSPACE_TIME_ZONE`), from the runs of jobs and unassigned recorded runs clipped to the period (replaced and deleted runs left out, a running run until now); only cells with a run are listed.
- `jobsByOutcome` (jobs starting in the period; running jobs and jobs without an outcome count as `unknown`) and `jobsByWeek` (every ISO week of the period, UTC, with zero weeks listed).
- `materialByMonth`: quantity and inventory value consumed per month and material type (the same consumption as material cost).
- `materialLossByType`: inventory value lost per type on failed or cancelled runs (net of their corrections) plus disposals and negative stock corrections other than job corrections.
- `materialChargesByType`: makerspace material of the period's jobs at the material rates of each job's active pricing snapshot, before price adjustments.
- `pricingGroups` (jobs, charges and discounts per pricing group of the active snapshot, "Unpriced" without one) and `pricingGroupMonths` (charges per month and group).
- In `totals` and `previousTotals`: `notBilled` (effective price of the period's ended jobs no order item refers to), `discounts` (how much price adjustments lowered the calculated price), `utilization` and `openDayUtilization`. Per machine: `utilization` and `openDayUtilization`. Utilization is the time runs occupied a machine as a percentage of the hours of the period that have passed; open-day utilization the same within scheduled open days of periods that are not drafts. Totals cover all machines that are not retired; a machine's value is capped at 100 %.

## Deleting jobs and runs

Deleting a job or a recorded run needs `machine_jobs.delete`; removing a manual run also works with `machine_jobs.edit` (migration 00044). Deletion is a tombstone (`deleted_at`, `deleted_by` on `machine_jobs` and `machine_runs`) because the inventory ledger is immutable and a connector would otherwise recreate a deleted recorded run with its next event. Display IDs are never reused. Deleted rows are excluded from lists, details (404), work items, overview, machine activity and metrics, statistics, the `machine_job_run_summaries` view, ledger job links and connector artifact targets. A deleted run is detached from its job (`job_id` is NULL).

- `DELETE /machine-jobs/{id}` with `{expectedVersion, reverseConsumption, deleteRecordedRuns}` returns 204. Manual runs are always deleted; recorded runs are deleted or detached into unassigned runs. A job with an order claim or an active order item answers 409 `job_on_order`.
- `DELETE /machine-runs/{id}` with `{expectedVersion, reverseConsumption}` deletes a run of any source and always returns 204 (clients refetch the job). The only remaining run of a job answers 409 `last_run`. A running recorded run may be deleted.
- `reverseConsumption` posts, per usage with net consumption in the ledger, a positive `adjustment` entry with reason `job_corrected` linked to the same run usage, at the consumption's unit cost: onto the spool while it is still active, otherwise into loose stock (the note says so). The usages are deactivated. Without it the ledger and usages stay untouched. Statistics count these entries like other usage corrections.
- Locks follow job, then runs. Audit events `machine_job.deleted` and `machine_run.deleted` commit with the mutation; audit metadata only allows UUIDs, so the choices are recorded as changed fields (`usages`, `inventory`, `recordedRunsDeleted`, `recordedRunsDetached`).
- Connector events for a deleted recorded run are stored (idempotency) with application state `recorded` and reason `run_deleted`; they never change or resurrect the run and book no consumption.

### Recycle bin

Deleted jobs and runs stay in a recycle bin (Workshop › Jobs › Recycle bin, `GET /machine-logbook/recycle-bin`, `machine_jobs.delete`; newest deletion first, at most 500 each). A deleted or detached run remembers its job in `machine_runs.former_job_id` (migration 00087).

- **Restore** (`POST /machine-logbook/recycle-bin/jobs/{id}/restore`, `…/runs/{id}/restore`, `{expectedVersion}`, `machine_jobs.delete`): a job comes back with the runs that went into the bin at the same moment and re-attaches the recorded runs its deletion detached as long as they are still unassigned; the job is settled again. A run comes back into its former job when that job is alive, otherwise as an unassigned run; a manual run whose job is in the bin answers 409 `job_in_bin`. Material a deletion reversed stays reversed (the ledger is immutable); a purged timelapse is gone. Audited as `machine_job.restored` (with `countRunsRestored`, `countRunsReattached`) and `machine_run.restored`.
- **Delete for good** (`DELETE /machine-logbook/recycle-bin/jobs/{id}`, `…/runs/{id}`, `{expectedVersion}`): removes the rows; usages, measures, reports and timelapse links cascade, a job takes the runs deleted with it, print files stay. A job or run whose material is booked in the inventory ledger cannot be removed, because the ledger is immutable and keeps its link to the usage: the API answers 409 `inventory_bookings_exist`, the bin marks such entries (`hasInventoryBookings`) and offers only Restore. Audited as `machine_job.purged` and `machine_run.purged`.
- **Confirmations.** Every delete in the UI asks first and says whether the item moves to the recycle bin (jobs and runs) or is gone for good (everything else).

## Bulk operations on the Jobs table

The Jobs table lists work items (jobs and unassigned recorded runs) and can act on a selection. Four endpoints apply the rules of the single operations to several items in **one transaction**: all-or-nothing, one audit event per affected job and run in the same transaction, and an optimistic version check per item (`{id, expectedVersion}`, at most 100 per list, no repeated IDs).

| Endpoint                                                                                                | Permission            | Single operation it repeats                                 |
| ------------------------------------------------------------------------------------------------------- | --------------------- | ----------------------------------------------------------- |
| `POST /machine-jobs/bulk-delete` `{jobs, runs, deleteRuns, material}`                                   | `machine_jobs.delete` | `DELETE /machine-jobs/{id}` and `DELETE /machine-runs/{id}` |
| `POST /machine-runs/bulk-create-jobs` `{runs, customer, operatorPersonId, notes?, pricingGroupId?}`     | `machine_jobs.create` | `POST /machine-runs/{id}/job`                               |
| `POST /machine-runs/bulk-combine` `{runs, title?, customer, operatorPersonId, notes?, pricingGroupId?}` | `machine_jobs.create` | `POST /machine-runs/{id}/job`, with all runs in one job     |
| `POST /machine-jobs/{id}/runs/bulk-attach` `{runs, replaceManualRuns, expectedJobVersion}`              | `machine_jobs.edit`   | `PUT /machine-runs/{id}/job`                                |

- **Blocked items refuse the whole request.** The service first locks and checks every item, then changes anything. If any item is blocked the answer is `409 bulk_blocked` and nothing changed; `details.items` lists every blocker as `{kind: job|run, id, displayId, code, message}`. Codes: `job_on_order` (delete), `run_assigned` (delete: a run listed under `runs` must be unassigned), `run_already_assigned`, `machine_retired`, `run_machine_mismatch`, `artifact_mismatch` (attach), `stale_write` (the item changed since `expectedVersion`) and `not_found`. The UI therefore filters blocked items first and shows them as "will be skipped"; the server check is the safety net for races. A stale job in bulk-attach answers a plain `409 stale_write`, an unknown job `404`.
- **Delete.** `deleteRuns` deletes the recorded runs of the listed jobs too, otherwise they are detached into unassigned runs; manual runs always go with their job. `material: reverse` restores the consumed material of every deleted run with compensating ledger entries (see above), `keep` or `null` leaves the ledger untouched. Materials are locked in ID order before any is restored. Running recorded runs are accepted like in the single delete; the UI skips them.
- **Create separate jobs** makes one job per run, named after the run's file (no title), numbered in the order the runs started, with the shared customer, operator, notes and pricing group. It answers `201 {jobs: [{id, displayId, title}]}`.
- **Combine** needs at least two runs and a single machine, because a job has one machine: runs on different machines answer `422 runs_on_different_machines` (after the blocker check). It answers `201` with the full job; the pricing snapshot is captured once.
- **Attach** takes one version check of the job, reverses and replaces its manual runs once with `replaceManualRuns`, and reprices the job once. Machine and print artifact rules are those of the single attach.
- **Audit.** Create, combine and attach write `machine_job.created` / `machine_job.run_attached` for the job and `machine_run.assigned` (metadata `jobId`) for each run; delete writes `machine_job.deleted` and `machine_run.deleted` as the single operations do.

The Jobs page no longer offers a row selection (the table lists jobs only, see [Jobs screens](#jobs-screens)); the bulk endpoints stay available to API clients, and the rules the former batch actions followed live on in `bulkWork.ts`.

## Consumption status, files and timelapses

### Consumption status

Every recorded run in run lists, run details and job details carries `consumptionStatus` (`null` for manual runs): `state` is `recorded`, `partial`, `missing` or `pending`, `reason` a stable `MachineRunConsumptionReason` and `detail` an optional machine-readable refinement. `machinelogbook.DeriveConsumptionStatus` applies these rules, first match wins:

1. A running run is `pending`/`run_in_progress`, except that a connector report `pending` with `artifact_on_internal_storage` (the print was started from the printer's internal storage and the connector has not found its 3MF on the USB stick or SD card yet; detail = the internal path as a code) wins and is shown while the run is still running. No other connector reason takes precedence over `run_in_progress`.
2. Usage entered by staff while nothing was booked from the machine is `recorded`.
3. Reported lines: a line is booked when it has a quantity, a quality other than `unresolved` and a spool; a line with segments counts each segment instead, booked when it has a quantity and a spool (a segment of 0 g needs none). All booked lines with machine usage give `recorded`, none `missing`, some `partial`. The reason is the first unbooked line's: an unresolved slicer line `no_slicer_weights_in_artifact`; an unresolved G-code line the connector's reason (`cancelled_before_first_layer`) or `gcode_estimate_unavailable`; a line without spool `slot_without_spool_assignment` when its slot is known, else `no_spool_mapping`; a segment without quantity (no split was possible) `segment_quantity_unavailable`, a segment without spool `segment_without_spool`. Bookable lines that inventory did not book (no stock, spool not consumable) are `inventory_not_booked`.
4. A legacy single-line report is `recorded` when booked, otherwise `missing` with `no_spool_mapping` or `inventory_not_booked`.
5. Without a report, the connector's run report decides: `pending` with its reason (or `consumption_pending`), or `missing` with its reason; an unknown connector reason becomes `consumption_not_reported` with the code as detail. See [printer connector](printer-connector.md#run-reports-why-consumption-is-missing) for the connector reasons.
6. Otherwise Core's own facts: a terminal outcome with reason `connection_timeout` is `missing`/`connector_offline_during_run` (detail `printer_connection_lost`), an unknown run whose connector was deleted the same with detail `connector_removed`, a run that ended less than 30 minutes ago `pending`/`consumption_pending`, an unknown outcome `outcome_unknown`, anything else `consumption_not_reported` (detail `artifact_missing` without a 3MF). This last case covers connectors older than this feature.

### Files and previews

`GET /machine-runs/{runId}/recording` and `GET /machine-jobs/{machineJobId}/recordings` (`machine_jobs.read`) return per recorded run (`MachineRunRecording`): display ID, source, state, start, `consumptionStatus`, the stored 3MF (`artifact`: id, original file name, size, SHA-256, parser status), its embedded `previews` (id, role `plate`/`model`/`other`, `plateNumber` for "Plate N", size, MIME type, `primary`; plates first by number), the `timelapse` (size, type, creation time, `expiresAt` from the retention setting), `timelapseStatus` and `commands` (the latest command of each kind). The job endpoint lists every recorded, not deleted run of the job, oldest first, so the job page can show the previews and files of all its runs with the run that contributed them.

Downloads need `machine_jobs.read` (the existing `/print-artifacts/...` endpoints still need `print_artifacts.read`) and always send `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`:

- `GET /machine-runs/{runId}/artifact/content`: the original 3MF as an attachment with its original file name.
- `GET /machine-runs/{runId}/previews/{previewId}/content`: a PNG or JPEG preview of the run's 3MF, `inline` for `img` elements; 404 unless the preview belongs to the run's artifact.
- `GET /machine-runs/{runId}/timelapse/content`: the video (`video/mp4`) as an attachment named `R-YYYY-NNNNNN-timelapse.mp4`. Single HTTP Range requests are answered with 206 (416 when unsatisfiable) on local storage, so a `video` element can seek; S3 storage streams the whole body with `Accept-Ranges: none`. Playing it in a `video` element needs `media-src 'self'` (or a matching `default-src`) in the frontend CSP.

### Interface

The run and job detail pages share one layout: a compact facts bar (runtime, material, outcome and machine or customer, everything else behind "Details") and a side column with the preview tile.

- **Run detail.** The preview tile shows one image per plate of the 3MF ("Plate N"; the largest plate render, while small copies and helper images such as the pick map are skipped; "Model" only for files without plate renders) with chevrons, arrow keys and a strip when there are several. The 3MF download sits over the bottom edge of the image. Recorded runs without a stored file or preview say so; manual runs have none. The timelapse tile plays the video inline (`preload="none"`, so opening the page transfers nothing) with a download button, or names the reason from `timelapseStatus` (not found, ambiguous, too large, disabled, expired). Recording data is only requested for recorded runs and refreshes every three seconds while a connector command is open.
- **Consumption reason.** When `consumptionStatus` is `missing`, `partial` or `pending`, a notification gives a sentence for every reason code plus the `detail`. With `machine_jobs.edit`, ended recorded runs also show "Fetch print file again" and "Recalculate consumption" below it (Carbon notifications take no interactive children), the state of the latest command of each kind (requested, running, done, failed with its reason code) and a clear message for 429 `run_command_rate_limited` and the 409 refusals. Recalculation is disabled while Core holds no 3MF. The runs table of a job shows a warning icon with the reason in a toggletip.
- **Spool segments.** "Reported material" lists a line fed by several spools as nested rows: spool label (a link with `inventory.read`), the article when it differs from the row above, grams, "from layer N" (else the start time) and "estimated by progress" for `split: progress`. A segment without spool is tagged "No spool"; ended runs offer editors (`machine_jobs.edit`, `inventory.read`) "Book … on a spool" for a segment without spool or grams, which opens the usual map dialog with the segment's grams prefilled and saves through the usage replacement, so the booked spools stay. Lines with segments are never offered as "Map filament N to a spool". `materialChangedDuringRun` shows the info notice "Material changed during the print".
- **Job detail.** The media card combines the print files and timelapses of all runs in one slideshow (see [Jobs screens](#jobs-screens)); the run page shows the same card for its run.
- **Recording settings.** Machines has a Recording tab for people with `machines.manage`: toggle for timelapse collection, retention in days (0 keeps until the run is deleted), the largest accepted video, how many videos are kept in all and how much storage they may take (the oldest go first; 0 means no limit), and the same four limits for print files (3MF): largest accepted file (up to 512 MiB), retention in days, count and total storage with their previews. A print file a running print uses is never removed; runs and jobs keep their records without the file.
- **Printer errors.** The printer setup shows the printer's current errors with their level (fatal, serious, common, info; common and info notices are folded away), the code as the printer shows it (`0300-0D00-0001-0001` for HMS codes, eight hex digits for print errors), the meaning the makerspace recorded for the code and a link to read more (the catalog's link, or the Bambu wiki page of an HMS code). Below it the error history of the machine (`GET /machines/{machineId}/printer-errors`, `machines.read`: open errors first, then those resolved within 30 days) can be cleared (`DELETE` the same path, `machines.manage`, audited as `printer_errors.cleared`); an error the printer still reports comes back with its next status. Meanings live in the error catalog (Workshop › Machines › Printers; `GET /printer-error-codes` is paged like the other lists, with `search` over code, meaning and description and `sourceFamily`/`source` filters; `PUT|DELETE /printer-error-codes/{sourceFamily}/{code}`, `machines.manage`, audited as `printer_error_code.saved|deleted`) and can be added straight from an error without a meaning. The catalog fills itself: the API fetches Bambu Lab's published list of HMS and print error codes with their English meanings (`PRINTER_ERROR_CODE_SOURCE_URL`, default `https://e.bambulab.com/query.php?lang=en`, the list Bambu Studio reads; empty turns it off) at start and every 24 hours (scheduler job `printererrors.sync`), and `POST /printer-error-codes/sync` (`machines.manage`, audited as `printer_error_codes.synced`) fetches now. Fetched rows carry `source: bambu` and are refreshed when the published text changes; a meaning written here (`source: manual`, also any fetched row someone edits) is never overwritten. The fetch is bounded (30 s, 16 MiB) and its state (`sync`: last attempt, last success, last error, how many codes) comes with every catalog page and is what the fetch returns; a failed fetch leaves the catalog as it is (migration 00089). Who is told about printer errors, finished runs and filament changes is set by the seeded central notification rules `printer_error`, `run_finished` and `filament_*` (Settings › Notification center; the Printers tab only points there). See [In-app notifications](notifications.md#system-notifications).
- **Machine events.** The run page lists the connector's events for the run in readable lines: states (a repeated state is shown once until it changes), printer errors with code, level, recorded meaning and link, filament changes with the slots, consumption reports and the outcome. `MachineRunEvent` carries `sourceFamily`, `code`, `transition`, `severity`, `title`, `link`, `fromSlot`, `toSlot` and `fileName` for that.

### Upload a 3MF afterwards

A print started from the printer's internal storage whose 3MF is on neither the USB stick nor the SD card has no file the connector can read (`artifact_on_internal_storage`; see [storage detection](printer-connector.md#storage-detection-of-a-bambu-print)). Staff with `machine_jobs.edit` upload the file on the run page ("Upload print file (3MF)", in the preview tile and the consumption notice) with `POST /machine-runs/{runId}/artifact`: raw body up to 512 MiB, header `X-File-Name` (percent-encoded), recorded runs only, in any state including running. The file is validated, parsed and stored exactly like a retrieved one (same parser, limits and deduplication by SHA-256) and linked to the run; `machine_runs.artifact_manual` remembers that staff uploaded it. Mutation, artifact creation and audit (`machine_run.artifact_uploaded`, `print_artifact.created`) commit in one transaction.

- **Replacing:** allowed only while the run's file was uploaded manually. A file the connector retrieved is never overwritten (409 `run_artifact_connector_retrieved`); manual runs answer 409 `run_not_recorded`. If the connector later retrieves a file itself, it supersedes the manual one.
- **Name check:** the file name and the 3MF's project name are compared with the run's print name (`file_name`, the printer's subtask name) case-insensitively without `.gcode.3mf`/`.3mf`; a trailing `...` (the printer truncates long names) matches as a prefix. A mismatch does not block the upload; the response has `nameMismatch` and the UI offers to keep the file or replace it.
- **Consumption:** for an ended run Core queues a `consumption_recompute` command (the response says `requested`, `already_requested` or `unavailable`); the connector calculates from Core's stored 3MF (slicer weights on success, G-code estimate up to the last layer on failure or cancel) and books it as usual. For a running run (`not_needed`) the connector fetches the stored file when the run ends. Core ignores a connector's `artifact_on_internal_storage` reason while it holds a 3MF. If the run's connector is gone, does not poll commands or is rate limited (`unavailable`), consumption stays missing and staff record the material manually.
- **Manual material:** the run page has "Edit material usage" (`machine_jobs.edit`) for recorded runs with or without a job, also while running. Staff usage keeps winning over machine reports; the run page warns when both exist.

### Re-fetch and recompute

`POST /machine-runs/{runId}/artifact-refetch` and `POST /machine-runs/{runId}/consumption-recompute` (`machine_jobs.edit`, CSRF) ask the connector that recorded the run to fetch the 3MF from the printer again or to calculate the consumption again from the stored 3MF (see [printer connector](printer-connector.md#commands)). They answer 202 with the new `MachineRunCommand` or 200 with the command of that kind that is still requested or running (idempotent). Refused with 404 for unknown or deleted runs and 409 `run_not_recorded`, `run_running`, `run_connector_unavailable` (assignment ended or connector not active), `connector_commands_unavailable` (the connector has not polled commands within five minutes, for example an older version) and, for recompute, `run_artifact_missing`. At most five commands per run within an hour: 429 `run_command_rate_limited` with `Retry-After`. Each request writes `machine_run.artifact_refetch_requested` or `machine_run.consumption_recompute_requested` (metadata `commandId`) in its transaction; the requesting account is only in the audit log. Command states are `requested`, `running`, `succeeded` and `failed` with `reasonCode`; Core fails commands not started within 15 minutes (`command_expired`) or running for more than an hour (`command_timed_out`).

### Timelapses and retention

Timelapse videos the connector uploads are private files linked to their run in `machine_run_timelapses` (one per run; migration 00078). `GET`/`PUT /machine-logbook/recording-settings` reads (`machine_jobs.read` or `machines.manage`) and changes (`machines.manage`, `expectedVersion`, audited as `run_recording_settings.updated`) the installation settings `timelapseEnabled` (default true; connectors read it with every configuration poll) and `timelapseRetentionDays` (default 90, 0 keeps videos until their run is deleted, at most 3650), `timelapseMaxBytes` (the largest accepted video, 1 MiB up to the deployment's ceiling `PRINTER_TIMELAPSE_MAX_BYTES`, shown as `timelapseMaxBytesLimit`; default 2 GiB; connectors read it with every configuration poll), `timelapseMaxCount` and `timelapseMaxTotalBytes` (how many videos are kept in all and how much storage they may take; 0 means no limit; migration 00085). The retention period is applied by the privacy retention engine; the count and storage limits by the five-minute maintenance pass, which deletes the oldest videos first and audits each as `machine_run.timelapse_trimmed`. Print files have the same four settings (`artifactMaxBytes` with the ceiling `artifactMaxBytesLimit` = 512 MiB, `artifactRetentionDays` with 0 = keep, `artifactMaxCount`, `artifactMaxTotalBytes`; migration 00086): uploads above the size answer 413 `artifact_too_large` (the connector then gives up on that file), the period is the legacy period of the privacy category "Print files and previews", and the count and storage limits are enforced by the maintenance pass, oldest first, skipping files a running print uses, audited as `print_artifact.trimmed`.

The API process runs a maintenance pass at start and every five minutes (like the survey delivery loop; safe with several replicas): it expires stale commands, deletes timelapses older than the retention in batches of 100 (`machine_run.timelapse_expired`, system actor, per run; the status then shows `expired`) and deletes queued storage blobs. Deleting a run, a job with its recorded runs or runs in bulk removes their timelapse and file rows in the same transaction (the run's `machine_run.deleted` audit lists `timelapse` among the changed fields) and queues the blob in `file_blob_deletions`; the next pass deletes it from storage. Downloads answer 404 immediately. Timelapses reference no person or account, so people merges do not touch them.

## Needs attention

`attention` lists what needs someone, each entry with a stable `code` and a short English `message`; it is empty when nothing does.

- **Jobs** (`MachineJob` and the job rows of `GET /machine-logbook/work-items`): `run_failed` (a run that is not replaced ended failed or cancelled), `consumption_unconfirmed` (a recorded run's consumption status is missing or partial, or still pending after the run ended), `no_recipient`, `not_on_order` (the job ended with an effective price above zero and neither an order claim nor an order item that was not removed refers to it), `needs_outcome`, `price_incomplete` and `order_outdated` (the claiming order item's snapshot is older than the job's billing revision; notes, operator and signage changes do not count). Unassigned recorded runs in the work-item list carry `run_failed` and `consumption_unconfirmed` only. The overview's active items carry none.
- **Machines** (`GET /machines`, `GET /machines/{id}` and the machine returned by create and update; machines embedded in jobs carry an empty list): `connector_offline` (the active, enabled assignment's connector sent no heartbeat for 90 seconds, never sent one, or reports the printer disconnected), `connector_error` (degraded, or an error code), `printer_error_open` (an error of the current assignment that has not cleared), `out_of_order` (status maintenance) and `runs_unassigned` (ended recorded runs without a job). Retired machines carry none.
- **Orders:** see [Orders](orders.md#needs-attention).

The work-item list computes the flags for a page with two extra queries (the runs of the page's items and the order facts of its jobs).

## Hiding a run from signage

`PUT /machine-runs/{runId}/signage-visibility` with `{hidden}` sets `machine_runs.hidden_from_signage` for a run that has not ended; an ended run answers 409 `run_ended` in both directions. Allowed for callers with `machine_jobs.edit` and for the operator or the person customer of the run's job (self scope); everyone else gets 403. The call writes `machine_run.signage_visibility_set` (ids and the field name only) in the same transaction and does not change the run version, so it never conflicts with a staff correction. The run detail page shows the checkbox while the run is live. Effect on the displays: see [signage.md](signage.md).

**Whole jobs.** `machine_jobs.hidden_from_signage` (migration 00097, `hiddenFromSignage` on `MachineJob`) keeps a job and all its runs off signage: a run counts as hidden when its job or the run itself is hidden, for the machine status, the camera and the timelapse widget alike (`MachineRun.jobHiddenFromSignage` tells the run page). The flag is set on `POST /machine-jobs`, `PUT /machine-jobs/{id}` (omitted keeps it), when a job is created from a recorded run (`POST /machine-runs/{id}/job`, bulk create and combine) and, optionally, when runs are attached to an existing job (`PUT /machine-runs/{id}/job`, bulk attach; null keeps it); all need the permission of the operation. Setting it never changes the job version, so orders do not see it as a change; the operation's audit event lists `hiddenFromSignage`.
